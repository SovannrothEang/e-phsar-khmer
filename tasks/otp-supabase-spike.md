# Spike 0.1 — what does account creation/login still need from the Supabase user?

Plan: "Own phone-OTP service on PlasGate" (Plans.md:26). Read-only investigation, branch feat/refine. No `.env` read. Anything not verified is marked `unknown`.

**Answer: nothing.** For the phone provider the Supabase user is used only as a yes/no proof that the OTP was right. No field of it is stored or used afterwards.

## 4. Risks

1. **Accounts created via Supabase that other code expects.** None found. Phone accounts store no Supabase id anywhere (`users` has no such column; the phone `user_auth_providers` row has NULL `provider_account_id`). Existing accounts keep working unchanged. Risk is only for Supabase `auth.users` rows themselves: they become orphaned and may later conflict if someone re-enables Supabase phone auth; `unknown` whether anything else (dashboard, RLS) reads Supabase `auth.users`. Social login (google/facebook) is unaffected and still mirrors the Supabase id into `provider_account_id`.
2. **Sessions / revocation.** Sessions are our own: access JWT (`jwt.secret`, default 15m) + refresh JWT (`jwt.refreshSecret`, 30d), both stateless, carrying `sid`. The server-side state is `user_login_devices` (db/schema/login-devices.schema.ts): `jwt.strategy.ts:52-76` joins on `sessionId` and rejects when `revokedAt` is set; `refresh()` does `touchActiveSession` (auth.service.ts:712-718). There is no refresh-token table. **To revoke all of a user's sessions on password reset:** add `LoginDevicesService.revokeAllForUser(userId)` calling the private `revokeWhere(eq(userId), isNull(revokedAt))` (login-devices.service.ts:467-476), which sets `revokedAt` and rotates `sessionId` per row. Existing `revokeOthers` (:292) cannot be reused as is: it needs a "current" device and throws `NO_ACTIVE_SESSION` (:297-302). Gap: tokens **without `sid`** (legacy, or minted when `recordLogin` returned null because no device headers — `recordLogin` returns `sessionId:null` when `device` is null, login-devices.service.ts:90) are NOT revocable this way; they stay valid until expiry (access 15m via jwt.strategy.ts:80-94; refresh 30d via auth.service.ts:740). To close it for reset, either require/mint a `sid` always, or add a `users.tokensValidAfter` timestamp compared with the JWT `iat` in `jwt.strategy.ts` and `refresh()`. Also note `UsersService.changePassword` (users.service.ts:595-601) does not revoke sessions either.
3. **DEV_OTP_TOKEN bypass** (`supabase.service.ts:45-59`, config `devOtpToken` configuration.ts:49). When the env var is set: `signInWithOtp` sends nothing and returns success; `verifyOtp` accepts exactly that fixed token for ANY phone and returns fake user `{id:'dev', phone}`. It is global (applies to register, login, phone-change) and has no NODE_ENV guard I could see (`unknown` whether config.validation.ts forbids it in production; not read). The new `OtpService` must reproduce it deliberately: when `OTP_PROVIDER=plasgate` and `DEV_OTP_TOKEN` set, skip the send and accept the dev token, and refuse to boot (or ignore it) if `NODE_ENV=production`. Do not let the bypass silently disappear, since the web e2e/dev flow depends on it, and do not let it leak into prod.
4. **Throttles on these endpoints** (`auth/auth.controller.ts:32-37`): global 100/min (env `THROTTLE_*`), plus `SMS_LIMIT` 5/min on `register`, `otp/request`, `otp/login`; `CREDENTIAL_LIMIT` 10/min on `login`, `otp/verify`, `telegram`. All keyed by IP (every route is `@Public`; `UserAwareThrottlerGuard` falls back to IP). In-memory storage, so per-instance. No per-phone limit and no attempt counter exist today (Supabase enforced those). Need per-phone limits in `OtpService` (plan assumption A1) and an attempts counter (5) on verify. Behind the Next server-action proxy all web users may share one egress IP (the comment at auth.controller.ts:106-108 says exactly this for social), so the 5/min per-IP SMS cap may throttle real users together; `unknown` whether the web forwards the client IP.
5. **Web client sends nothing Supabase-specific for phone OTP.** `apps/web/actions/otp.ts` posts `{phone}`, `{phone,password}`, `{phone,token,password,firstName,lastName}` with `x-device-*` headers to our API; `actions/register.ts:24` posts `/auth/register`. Token length: `VerifyOtpDto.token` is `Length(4,8)` (verify-otp.dto.ts) and the UI waits for `OTP_LENGTH` (6) digits and auto-submits (OtpVerifyForm.tsx:~100-110). Supabase-specific bits in web are only social login (`SocialCallback.tsx`, `lib/auth/social.ts`) and storage uploads. UI gap: the resend cooldown is hard-coded (`RESEND_COOLDOWN_SECONDS`, OtpVerifyForm.tsx:~128) so it must read `retryAfterSeconds` from the API; web `requestOtp` drops everything but `success` (actions/otp.ts:45-47).
6. **Race on register.** `mirrorSupabaseUser` phone branch uses `onConflictDoUpdate` on `users.primaryPhone` (partial unique, active only) — concurrent verifies are safe for the row, but `generateUniqueUsername` (auth.service.ts:267) has the known check-then-insert race (CLAUDE.md known gap). Unchanged by this plan.
7. **Verify oracle:** `verifyPhoneOtp` checks the password before the OTP (:188-191); keep it so a stolen phone cannot be used to probe, and so wrong passwords never burn OTP attempts. Same-401 messages: `INVALID_CREDENTIALS` vs `Invalid or expired OTP` already differ; fine for login (not enumerating), keep.

## 5. Recommended minimal design for the verify step (no Supabase user)

- `phone_otps(id, phone, purpose enum('register','login','reset'), code_hash, attempts int default 0, expires_at, consumed_at, created_at)`; index on `(phone, purpose, created_at desc)`. `code_hash = HMAC-SHA256(OTP_HMAC_SECRET, phone|purpose|code)`; 6 digits via `crypto.randomInt`; expiry 5 min.
- `issue(phone, purpose)`: enforce per-phone resend wait and daily cap, invalidate older unconsumed rows for that phone+purpose, insert, send via `PlasGateClient` directly (never the outbox), return `{ retryAfterSeconds }`. Record a delivery row without the code.
- `verify(phone, purposes[], code)`: load latest unconsumed, unexpired row for the phone; if `attempts >= 5` fail; `attempts++` (atomic UPDATE ... RETURNING); compare with `timingSafeEqual`; on match set `consumed_at` in the same statement (`UPDATE ... WHERE consumed_at IS NULL RETURNING`) so a code is single-use under concurrency. Return boolean; never reveal which condition failed.
- `verifyPhoneOtp` calls `verify(phone, ['register','login'], dto.token)` at :207; replaces `data.user` with nothing; then the existing branches (revive / complete bare account / upsert) run unchanged, and `stampPhoneVerified` + `finishLogin` unchanged. Resend (`otp/request`, phone only) chooses purpose = `login` if an active user with that primary phone exists, else `register`; that matches what verify accepts.
- Forgot-password: request always answers `{ otpSent: true }` (A3); send only if an active user with that primary phone exists (and not banned). Reset: `verify(phone, ['reset'], code)` -> `bcrypt.hash(newPassword, PASSWORD_SALT_ROUNDS)` -> update `users.passwordHash` -> revoke all sessions (§4.2) -> optional `stampPhoneVerified`. Do not auto-login; make the user sign in.
- `OTP_PROVIDER=supabase|plasgate` switch lives inside `OtpService` (or a thin `OtpProvider` seam): `supabase` delegates to the existing `SupabaseService.signInWithOtp/verifyOtp` so rollback is a config flip. Under the `supabase` provider forgot-password is unavailable (`unknown` whether Supabase's OTP can serve it; it would verify but cannot rate-limit/revoke), so reject with a clear error.
- Tests: mock `OtpService` in `auth.service.spec.ts` in place of the Supabase mocks; add `OtpService` unit tests for expiry, attempts exhaustion, single use, resend wait, dev token.
