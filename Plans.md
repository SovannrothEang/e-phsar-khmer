### Plan: Reliable SMS delivery — queue it, retry it, rate-limit it, record it, text only verified phones (2026-11-02)

**Purpose**: `SmsNotificationChannel` (PlasGate) currently sends inline inside `NotificationsService.notify()`: the caller waits up to 10 s, a failure is swallowed (SMS lost), nothing keeps under PlasGate's 200 requests/minute, nothing records what was sent, and it texts `primaryPhone` even though that number may not be the user's. Make SMS a durable, retried, rate-limited, audited delivery that only reaches verified phones, without ever making the in-app notification depend on it.

**Spec delta**: no root `spec.md`. Record in `ARCHITECTURE.md` (notifications section): "SMS is opt-in per notification (`data.sendSms === true`). It is delivered by an outbox event `notification.sms.requested`, never inline. Each attempt outcome is recorded in `sms_deliveries`. Only a user whose `primaryPhone` is OTP-verified (`phoneVerifiedAt`) is texted. The in-app row never depends on SMS."
**team_validation_mode**: `manual-pass` (no sub-agents; perspectives assessed alone). Memory not checked: harness-mem was not queried (`not_observed != absent`).
**Evidence (read this session)**:

- `NotificationsService.notify()` runs every channel with `Promise.all` (`notifications.service.ts:30`); the SMS channel is the third entry in `NOTIFICATION_CHANNELS` and catches all errors.
- The outbox already provides what is needed: `OutboxHandler` returns `published | retry | failed`, has `onAbandoned` and `redact`, and `IntegrationEvent` supports `dedupeKey` and per-event `maxAttempts` (`outbox/outbox.types.ts`). `PaymentSettledOutboxHandler` is the in-repo pattern to copy.
- `users.phoneVerifiedAt` exists and is written by the phone-change flow (`users.service.ts:642`).
- PlasGate: `POST https://cloudapi.plasgate.com/rest/send?private_key=…`, header `X-Secret`, body `{sender,to,content}`, 200 requests/minute. Current live response: `400 Invalid Sender`.
  **Not observed (`unknown`)**: whether a failed `retry` outcome counts against `maxAttempts` (matters for the rate limiter, task 1.4); whether the login/registration OTP flow sets `phoneVerifiedAt` (the CLAUDE.md gap says it is never written, but `users.service.ts:642` writes it, so that note may be stale); PlasGate's exact error codes for rate-limit versus bad number; whether Redis is reachable from every deployed instance (ChatPubSub uses it); the approved sender id.
  **Assumptions to confirm**: (A1) SMS stays opt-in via `data.sendSms`. (A2) We keep the outbox rather than add BullMQ. (A3) Message text is never stored in `sms_deliveries` (it can carry codes); only status, masked phone and provider reply. (A4) Existing unverified numbers are not backfilled as verified.
  **Perspectives (manual-pass)**: _Product_: payment and security texts must arrive or be visibly failed, never silently dropped. _Architecture_: reuse the outbox; the producer enqueues, a handler delivers; the rate limit must be shared across instances or it is `limit × instances`. _Security_: sender/keys come from env and are never logged; message body redacted from the outbox payload after delivery; verified-phone gate stops texting a number someone else claimed. _QA_: failure classes (retry versus permanent) are the part most likely to be wrong, so they get tests first. _Skeptic_: retries during a burst could burn the attempt budget and abandon good messages, hence the burst test in 1.4; do not widen scope to all notification types.
  **Lint / formatter baseline**: present. Verification: `pnpm --filter backend lint`, `pnpm --filter backend test`, `pnpm --filter backend build`.

### Plan: Bakong demand-driven polling — poll only while a payment is open (2026-10-31)

**Purpose**: Bakong has no webhook or push, so something must ask. Make that asking happen only while a payment is open (armed by issue, idle when none), with one poller and batched calls, instead of a BullMQ chain plus a 15 s reconciler that both ask per attempt. Settlement durability is out of scope: the owner tested that a paid QR settles after a page refresh.

**Spec delta**: no root `spec.md`. Record in `payment/providers/bakong/README.md` and `ARCHITECTURE.md`: "Polling is demand-driven: armed when a payment is issued (first `payment.attempt.poll_requested`), idle with zero open attempts. Settlement is server-driven and independent of any client; the UI only reads state."
**team_validation_mode**: `manual-pass` (no sub-agents).
**Not observed**: whether `check_transaction_by_md5_list` exists in NBC's official docs (only third-party SDKs mention it, max 50 per call); whether Bakong rejects payment of an expired dynamic KHQR; whether `DATABASE_URL` is a pooler (secret, not read). `not_observed != absent`.
**Rejected**: Postgres LISTEN/NOTIFY. It needs a long-lived session connection (impossible on serverless), NOTIFY is lossy so a table sweep is still required, and Bakong never notifies us. **Known gap on serverless**: no live instance means no poller. A paid QR waits until a request boots one. Task 2.1 decides the wake-up.

### Plan: Keep E2E, stop the "Sent before this device was set up" wall (2026-10-26)

**Purpose**: a second browser, a cleared profile or a new phone shows a run of "Sent before this device was set up. Restore your history with the backup passcode." Keep end-to-end encryption exactly as strong, but make a new device read as much history as the account can possibly give it, and say something useful about the rest.

**Spec delta** (`docs/e2e-encryption.md`, new section "History availability"; there is no root `spec.md`): a message is readable on a device iff (a) the message carries an envelope for that device, or (b) some device of the account **decrypted it while holding the backup key (BK) and uploaded it**. Today (b) is true only for messages a device happened to _display_. This plan makes it true for every message a signed-in device _received_. Private keys, ratchet sessions and BK never reach the server in the clear (unchanged). The "Encrypted backup / key recovery" non-goal in that file is out of date and is rewritten.
**team_validation_mode**: `manual-pass` (no sub-agents; Product, Architecture, Security, QA and Skeptic considered by hand).
**Lint/formatter baseline**: present (eslint, prettier, `tsc`, `pnpm --filter web test` = `node:test` over `lib/**/*.test.ts`, backend jest). No setup task.
**Reuse check**: `lib/e2e/stub-engine.ts` already exists for tests; `startVisiblePoller`, `useNotificationEvents`, `fetchInbox`, `fetchMessages` and `decryptMessage` are reused as they are. Nothing new on the crypto side.
**Not observed**: how many of the unrecoverable messages in the dev DB were never displayed on any device (segments are ciphertext under BK, so this cannot be counted from the server).

**Risks and residual limits (stated, not hidden)**:

1. **A message to a stale device is readable only if the seller returns on that same browser.** If they return on another browser or after clearing data, that browser is a new device with no envelope for it, and only the history backup can help (the "Keep E2E, stop the wall" plan). K2.1 trades silent refusal for this limit, which is what Signal-style systems accept. The sender's UI should not promise delivery on read (no change planned).
2. **Held plaintext sits in the buyer's IndexedDB** until sent or expired, the same exposure as the decrypted-message cache that already exists there.
3. **The nudge reveals that someone wants to talk**, never what they said. Rate limit and block check are in the DoD.
4. **K2.1 changes the envelope set the server validates.** Every place that computes the set must go through the one helper, or sends loop on `E2E_DEVICES_MISMATCH` (covered by the list-versus-load test and K4.1 scenario 3).
5. The pending locale/UI WIP in the working tree overlaps K2.2; land or commit it first.
6. The web app has no component test framework, so K1.1, K1.3, K3.2 and K3.3 are verified in a browser.

**Owner decisions (defaults proposed; veto any)**: D1 held-message lifetime 14 days. D2 nudge goes in-app and to Telegram when linked. D3 stale fallback keeps the 2 most recent devices. D4 production census (K0.1) allowed read-only, or dev only.
