# PhsarKhmer Architecture

This is the current architecture guide for the PhsarKhmer monorepo. It records the system structure, module boundaries, API behavior, data flows, and implementation details that are easy to lose when changing one feature at a time. Verify time-sensitive details against the code before relying on them.

## Approach and boundaries

The system is a TypeScript modular monolith managed with pnpm and Turborepo. Keep feature boundaries clear, evolve the monolith as needs emerge, and extract services only when there is a concrete operational or ownership reason. The backend uses strong typing, OpenAPI contracts, and PostgreSQL as its source of truth. Avoid distributed infrastructure and patterns such as Kafka, microservices, or CQRS unless a feature explicitly requires them.

## Backend architecture

### Request lifecycle

```
Request
  → IdempotencyMiddleware  (POST/PATCH/PUT only; middleware runs before guards)
  → JwtAuthGuard          (global APP_GUARD #1)  ← skipped if @Public()
  → UserAwareThrottlerGuard (global APP_GUARD #2) — keys on req.user.id when JwtAuthGuard set one, else IP
  → ValidationPipe (whitelist + transform)
  → Handler
  → ResponseInterceptor  → { success, data, meta? }
  → GlobalExceptionFilter  (on throw)
```

JwtAuthGuard runs first specifically so the throttler can see `req.user` — a fairness fix for shared-NAT traffic (one busy office/campus no longer shares a single IP-keyed bucket). `UserAwareThrottlerGuard` (`common/guards/user-aware-throttler.guard.ts`) falls back to IP for anonymous/public requests, where `req.user` is never set.

### Deployment model (`APP_ROLE`)

`APP_ROLE=api|worker|all` (default `all`) picks the shape of the process (`src/config/runtime-role.ts`):

| Role     | Serves HTTP    | Background work                                                                  |
| -------- | -------------- | -------------------------------------------------------------------------------- |
| `api`    | yes            | none — no BullMQ `Worker`, no housekeeping or polling timer                      |
| `worker` | yes (same app) | BullMQ workers, outbox drain + retention, account purge, payment reconciler      |
| `all`    | yes            | both — the single-process shape every local run and deploy had before the switch |

- **`api` starts no BullMQ `Worker`.** A `@Processor` provider makes BullExplorer construct a `Worker`, which opens a dedicated blocking Redis connection per processor; dropping the provider from the module is the only way not to open them. The same role gates the background timers through `configuration.ts` (`outbox.workerEnabled`, `accounts.purgeEnabled`, `payment.reconcilerEnabled`). An outbox row written by an `api` instance is therefore drained by whichever worker instance polls next, bounded by `OUTBOX_POLL_INTERVAL_MS` (default 30 s). The chat WebSocket heartbeat still runs — it is part of serving live connections, not a background sweep.
- **`APP_ROLE` is read from the raw process environment while the module graph is built**, before `ConfigModule` loads `.env`. On a host it must be a real environment variable (Vercel project env, a shell export), not a `.env` line: a `.env`-only value used to be described as benign and it is not — the module graph would keep `all` (five blocking Redis connections) while the validated config applied `api` (pool 5, every background timer off), the inverse of the budget this switch exists to enforce. `wiredAppRole` (`src/config/runtime-role.ts`) is captured once at import time so the two readings cannot drift, and `assertRoleIsExported` fails the boot when `configuration()` sees a role the module graph never did. The boot line logs the resolved role and whether background work is on.

**Postgres connection budget.** One postgres.js pool per process, shared by the whole backend (every module, not just chat). `DATABASE_POOL_MAX` defaults by role — `api` 5, `worker` 15, `all` 20 — and is capped at 20, because every instance's pool counts against the same Supabase project connection limit. Connection lifecycle: `DATABASE_CONNECT_TIMEOUT_SECONDS` 10, `DATABASE_IDLE_TIMEOUT_SECONDS` 60 (returns a connection to the pooler while an instance idles), `DATABASE_MAX_LIFETIME_SECONDS` 1800. `DATABASE_STATEMENT_TIMEOUT_MS` and `DATABASE_LOCK_TIMEOUT_MS` stay `0` (off) unless the connection is direct: they are sent as Postgres startup parameters, and Supabase's transaction-mode pooler rejects parameters it does not know.

**Authenticated cron tick.** A host that scales to zero never keeps an instance warm long enough for the hourly outbox-retention sweep or the 6-hourly account purge, so `POST /api/v1/internal/jobs/run` runs one pass of both on demand (`src/internal/internal-jobs.controller.ts`). It takes the same `x-internal-secret` header and `INTERNAL_RECONCILE_SECRET` value as `POST /api/v1/internal/payments/reconcile`, and fails closed the same way: unset secret → 503, wrong or missing header → 401. Both sweeps are idempotent predicates, so calling it from a cron is harmless while a `worker`/`all` instance runs them on their own schedule too. The response is `{ outboxPurged, accountsPurged }`.

### Auth model

- `@Public()` on a handler or controller class bypasses `JwtAuthGuard` entirely. Without it, a valid `Bearer` token is required.
- JWT payload is `{ sub, role, sid?, gen? }`. `role` is `'user' | 'admin' | 'super_admin'`; the guards match roles literally, so `@Roles('admin')` excludes a `super_admin` and a route both tiers may use names both. `JwtStrategy.validate` (`src/auth/strategies/jwt.strategy.ts`) checks the DB, rejects soft-deleted users (`deletedAt` set), rejects the chat WS ticket and the password-reset proof by `typ`, validates the device row when `sid` is present, and applies the `users.tokensValidAfter` cutoff. Tokens without `sid` (legacy, admin, social/Telegram) are grandfathered.
- Use `@CurrentUser() user: RequestUser` — `{ id, role, sessionId? }`.
- Dual tokens: short-lived `accessToken` (default 15 min) + long-lived `refreshToken` (default 30 d). `refreshToken` uses a separate `JWT_REFRESH_SECRET`, and the boot fails if the two secrets are equal.
- **Refresh rotation with reuse detection.** `gen` is the row's `refresh_epoch`: `LoginDevicesService.rotateRefreshToken` bumps it in one conditional `UPDATE` (`refresh_epoch = <presented>`), so exactly one caller holding a given token can rotate. A loser inside `REFRESH_REUSE_GRACE_SECONDS` (30 s) is a parallel-tab race and gets reissued at the winning generation; anything older is treated as a stolen token and **revokes the whole session** (`reused` → `401 Refresh token reused`). Tokens with no `gen` (already-issued) are read as generation 0.
- Soft-delete is enforced at all three entry points: `loginWithPassword`, `refresh`, and `JwtStrategy.validate`.
- Device sessions: `user_login_devices` is the revocation anchor; login clients send `x-device-id` / `x-device-name` / `x-device-info`, and `sid` is the revocation epoch (login reuses it, revoking rotates it). Endpoints: `GET /auth/devices`, `DELETE /auth/devices/:id`, `POST /auth/devices/revoke-others`, `POST /auth/logout`.
- **Suspension is a session-ending state, and it explains itself (2026-11-08).** `users.status='suspended'` is set by staff together with `statusReason` / `suspendedAt` / `suspendedById`, and the same transaction sets `tokensValidAfter = now()` and `revokedAt = now()` on every non-revoked `user_login_devices` row — so every access token, refresh chain and device session dies at once. Every login path answers `403 { code: 'ACCOUNT_SUSPENDED', message: <reason>, details: { reason, support: { email, telegram, phone } } }` (contacts read from `app_settings`, each key omitted when unset) — the `details` slot exists because the exception filter forwards only `code` and `details`, and this is the only surface a suspended account can see: there is no read-only mode, no browse-while-suspended path, and no in-app notice it could log in to read. The WS handshake now applies the same `status !== 'active'` check the REST strategy always had, and a suspension publishes to the chat pub/sub channel so that user's live sockets close. Reinstatement is manual (`status='active'`); nothing in the app lifts it automatically.

### Auth flow — phone registration & login (OTP + password)

```
POST /api/v1/auth/register   { phone }                        → sends OTP via Supabase (or dev bypass)
POST /api/v1/auth/otp/request { phone }                       → re-sends OTP (public; E.164-validated via RequestOtpDto)
POST /api/v1/auth/otp/login  { phone, password }              → login-mode: validates credentials, THEN sends OTP (unknown phone / wrong password → 401, no SMS)
POST /api/v1/auth/otp/verify { phone, token, password,
                              firstName?, lastName? }         → verifies OTP; creates the account (register) or logs in the existing user
```

`verifyPhoneOtp` is the single creation/login chokepoint. It looks up the active user by `primaryPhone` first:

- **User exists** — the submitted `password` must match (`bcrypt.compare`); mismatch → 401 **before** any OTP is consumed. The conflict path can never overwrite credentials: payload extras land only in the INSERT `.values()`, while `onConflictDoUpdate.set` stays `{updatedAt}` (locked by a unit test). Even a replayed body with a fresh password/names/username is ignored.
- **User absent or a legacy bare account** (null `passwordHash` — created before passwords were required) — the verify **completes the account in place**: bcrypt-hashes the password (10 rounds), stores `firstName`/`lastName`, and generates a unique username via `generateUniqueUsername(buildUsernameBase(first,last))` → `sok-dara`, `sok-dara-2`, …. Names carry from the web register form; a phone-digit fallback is deliberately avoided so the nicer name-based handle stays free.
- Verify **without** `password` is a 400 — there is no passwordless login path (the public `otp/request` resend can never be a backdoor).

`mirrorSupabaseUser` in `auth.service.ts` upserts users without a Supabase-specific ID: phone auth conflicts on `primaryPhone`; social auth resolves in order — existing `(provider, providerAccountId)` link, then a local account with the same email **only when that account's own `emailVerifiedAt` is set**, then a new account stamped verified from the provider-confirmed email. An unverified collision is a 409 `EMAIL_LINK_REQUIRED` (sign in with the existing method, then link from Settings); a changing email clears `emailVerifiedAt` so a stale flag cannot be re-used. Both paths insert into `user_auth_providers` and `user_phones` (isPrimary: true) when a phone is present. Soft-deleted phones don't conflict (partial index with `WHERE deleted_at IS NULL`) — a fresh row is created with the extras.

### Phone OTP (`src/otp/`)

`OTP_PROVIDER=supabase|plasgate` (default `supabase`) picks who issues and checks phone codes for register, resend, login-by-OTP and verify. Under `plasgate`, `OtpService` generates a 6-digit code (`crypto.randomInt`), stores only `HMAC-SHA256(OTP_HMAC_SECRET, phone|purpose|code)` in `phone_otps` (purpose `register` / `login` / `password_reset`), and checks it with `timingSafeEqual`: 5-minute expiry, at most 5 guesses (the attempt is spent before the compare, so parallel guesses cannot exceed it), single use, a new issue kills the older open code. `verifyPhoneOtp` keeps its order (ban, password check, then OTP) so a wrong password never burns an attempt. `DEV_OTP_TOKEN` still works outside production and is ignored (error logged) when `NODE_ENV=production`. Flip `OTP_PROVIDER` back to `supabase` to roll back with no code change.

**Why OTP bypasses the notification outbox.** `OtpSmsSender` calls `PlasGateClient` directly (after `SmsUserLimiter` and `SmsRateLimiter`, one quick retry in the request). The outbox would persist the message, and therefore the code, in `outbox_events.payload` until the event is terminal, and its SMS rows are keyed on `users.id`, which a registering phone does not have yet. `sms_deliveries` gets an audit row with a masked phone and no message text (`userId` null, `purpose` set). Limits are per phone, not per user: `SMS_USER_COOLDOWN_SECONDS` (300) per phone and purpose and `SMS_USER_DAILY_CAP` (10) per phone per day, both failing closed when Redis is down, answered as 429 `OTP_COOLDOWN` (with `retryAfterSeconds`) / `OTP_DAILY_CAP`; the per-IP `@Throttle` (`SMS_LIMIT` 5/min, `CREDENTIAL_LIMIT` 10/min) still applies.

**Forgot password uses the own OTP service when `OTP_PROVIDER=plasgate`.** The service's `password_reset` purpose is wired into the shipped three-step reset (below): the request step issues a hashed, single-use code through `OtpSmsSender` (detached send, per-phone limits) and the verify step checks it with `OtpService`. Under the default `supabase` provider the same endpoints keep using Supabase OTP. The two-endpoint `/auth/password/forgot|reset` design from the plan is not exposed.

**Session revocation.** Device rows (`user_login_devices`) only reach tokens carrying a `sid`; tokens minted without device headers have none. The password-reset confirm revokes every device row with `LoginDevicesService.revokeAll` **and** sets `users.tokensValidAfter` in the same transaction, so tokens without a `sid` die too. `JwtStrategy.validate` and `AuthService.refresh` reject any token whose `iat` is older than that cutoff (`auth/token-cutoff.util.ts`); `iat` has one-second resolution, so the cutoff compares at second precision. `UsersService.changePassword` sets the same cutoff (since 2026-11-03), so a settings password change ends the sessions minted before it — the very next request from an old access token is rejected, and the client signs in again — and any outstanding password-reset proof stops working. It does not delete `user_login_devices` rows (only the reset flow calls `revokeAll`), so the devices page can still list a session that can no longer refresh. Phone-change OTP (`users.service.ts`) is still on Supabase.

### Password reset (shipped 2026-11-02)

Three public endpoints, identifier-based (phone, username or email; email matched case-insensitively):

```
POST /api/v1/auth/password/reset/request { identifier }              → { otpSent: true } always
POST /api/v1/auth/password/reset/verify  { identifier, token }       → { resetToken } (10 min, typ: password_reset)
POST /api/v1/auth/password/reset/confirm { resetToken, newPassword } → { reset: true }
```

The request step resolves the identifier and texts the account's E.164-normalized `primaryPhone`, always answering `{ otpSent: true }` — unknown, inactive, banned or phone-less accounts are indistinguishable and are never texted. Delivery follows `OTP_PROVIDER`: `supabase` (default) calls `SupabaseService.signInWithOtp`; `plasgate` calls `OtpSmsSender.issueAndSendDetached` with purpose `password_reset` (hashed 6-digit code, 5-minute expiry, 5 attempts, per-phone cooldown/daily cap). The send is detached so PlasGate latency or failure cannot reveal whether the account exists, and limiter outcomes are swallowed so the response stays uniform. The verify step consumes the single-use code (`OtpService.verify` under plasgate, Supabase under supabase) and mints a 10-minute `typ: password_reset` JWT; every failure — including attempt exhaustion — is the same 401. Confirm checks the proof, writes the bcrypt(10) hash, sets `users.tokensValidAfter` and revokes every device-bound session in one transaction, then writes a best-effort `security.password_changed` notification. No tokens are minted — the web sends the user to `/login`. `DEV_OTP_TOKEN` is a boot error in production and the reset flow opts out of it on both providers (`devBypass: false`), so the plasgate path always issues a real code. Social-only accounts with no phone cannot reset. The web form is `components/auth/Forgot-PassowordForm.tsx` + `actions/password-reset.ts`.

### Database access

`DbModule` is `@Global()` — never import it in feature modules. Inject the typed Drizzle client with `@Inject(DRIZZLE) private readonly db: DbClient`. For raw SQL (e.g. health ping), inject `@Inject(PG_CLIENT) private readonly sql: postgres.Sql`.

Drizzle is configured with `casing: 'snake_case'`: write schema column names in camelCase; the driver maps to `snake_case` in the DB automatically.

Schema files live in `src/db/schema/` and are re-exported from `src/db/schema/index.ts`. Add new tables there.

### Supabase

`SupabaseModule` is `@Global()` — never import it in feature modules; inject `SupabaseService` directly. It exposes one admin client (service-role key) and a helper to create a user-scoped client. Auth (OTP, social OAuth, token validation) and storage operations go through `SupabaseService`.

`signInWithOtp` and `verifyOtp` support a dev bypass via `DEV_OTP_TOKEN` env var — when set, no SMS is sent and that fixed token is accepted. Keep the value at 6 digits or fewer — the web OTP input (`apps/web/components/auth/OtpVerifyForm.tsx`) has 6 single-digit boxes, so a longer token can never be entered. Currently `000000` in `apps/backend/.env`; changing it requires a backend restart. In dev, the Supabase-side fake user id is the literal string `'dev'`; the local `users.id` is DB-random (`defaultRandom`), and repeat-login identity is guaranteed by the `primaryPhone` upsert in `mirrorSupabaseUser`.

### Response envelope

`ResponseInterceptor` wraps all non-string handler return values:

```json
{ "success": true, "data": <value>, "meta": <pagination?> }
```

String return values pass through unwrapped (preserves `GET /` → `Hello World!`). Errors from `GlobalExceptionFilter` have shape `{ "success": false, "error": { "code", "message", "details?" } }`.

### Idempotency

`IdempotencyMiddleware` runs on POST/PATCH/PUT. Clients include an `Idempotency-Key` header. The middleware hashes the request body (SHA-256) and stores key+method+path+user in the `idempotency_keys` table (unique with `NULLS NOT DISTINCT` so anonymous requests dedupe too). Because middleware runs before guards, it verifies the `Bearer` token itself (via `JwtService`) to resolve the user; invalid/absent tokens are scoped as anonymous (`user_id NULL`). First-request detection uses `INSERT … ON CONFLICT DO NOTHING … RETURNING`: a returned row means "we own it, proceed"; a conflict means 422 (a different body hash, whatever the row's state), replay (completed), 409 (processing < 30 s), or reclaim (failed or stale-processing rows are flipped back to processing — conditionally on the `lockedAt` read, so two racing retries cannot both proceed). A 5xx response is recorded as `failed`, not cached, so the retry re-executes (2026-10-23).

### Categories i18n

Categories and subcategories use **four tables**, not two:

| Table                      | Purpose                                            |
| -------------------------- | -------------------------------------------------- |
| `categories`               | Structure only (slug, icon, sort_order, is_active) |
| `subcategories`            | Structure + `field_schema` JSONB                   |
| `category_translations`    | `(category_id, locale, name, description)`         |
| `subcategory_translations` | `(subcategory_id, locale, name, description)`      |

Supported locales: `'en' | 'km'` (the `localeEnum` pgEnum). Locale is resolved from the `Accept-Language` request header via `resolveLocale()` in `src/categories/locale.util.ts`.

`CategoriesService` uses **two aliased LEFT JOINs** per query (one for the requested locale, one for `'en'`), then COALESCE in JS:

```ts
name: row.reqName ?? row.enName ?? row.cat.slug; // slug is the last resort
```

**`field_schema` JSONB** stores a `FieldDef[]` array describing the listing creation form fields for that subcategory. The web post form **consumes it at runtime** (schema-gated blocks in `ListingPostForm.tsx`): every block renders iff its key is present, so a key with no render block vanishes silently — that comparison is the opt-in checklist. Required-ness is hardcoded per block, never read from the schema's `required` flag. `FieldDef` type is defined in `src/db/schema/categories.schema.ts` — key, label (i18n), type (`text | number | select | boolean | price | discount | photos | location | contact | product`), required, options?, max?.

When populating `field_schema` from a `spec-detail-*.md` file (see "Frontend listing-form specs"), copy the conventions already used by the seeded categories (cars/phones/computers/electronics/home-and-land/jobs/services/fashion-and-beauty/furniture-and-decor/books-sports-and-hobbies/pets/foods) so entries stay consistent: reuse the module-level `conditionField` const in `categories.seed.ts` (do not redefine it); write photos inline as `{ key: 'photos', type: 'photos', max: 8 }`; map "Name / Phone Number (up to 3) / Email" to `contactName` / `contactPhones` (`max: 3`) / `contactEmail` (all `type: 'contact'`); fold "Address" + "(set on Google Maps)" into a `location` field plus a `text` `address` field (there is no separate maps field); key any "Type" picker as `type` with `type: 'select'` + `options`; labels are `en`-only. Use `type: 'number'` for a free numeric quantity and reserve `select` for enumerable numerics (`storage`, `year`). Home & Land's `size` is the one `number` key today, and **its unit lives on the display rather than in the input**: the post form renders a bare number with no suffix (what the captain's form mock shows), while the published specs grid appends `m²` via `VALUE_SUFFIX` in `ListingSpecs.tsx` — so the JSONB stores `"220"` and the detail page reads `220m²`. (This file has now been wrong in both directions on that detail: it first asserted the `m²` was in the form, then that no `m²` existed anywhere. Both surfaces are stated here as shipped.); reuse `conditionField` only when the form actually has a Condition field — not every category does (Home & Land forms carry no Condition/discount/free-delivery fields). The seed upsert in `src/db/seed.ts` writes `field_schema` on conflict, so re-running `db:seed` is idempotent. (Counting tip: `grep -c "fieldSchema:"` skips the `fieldSchema?:` type-def line.) When a spec-detail file states all subcategories of a main category share one form (Jobs/`spec-detail-six.md` and Services/`spec-detail-seven.md` both say "the same form"), apply one identical `fieldSchema` array to every subcategory. **The photos `max` is per-category — read each spec's own `Photo (0/N)` line; never generalize across categories:** Jobs (`spec-detail-six.md` = `Photo (0/1)`) → `max: 1`; Services (`spec-detail-seven.md` = `Photo (0/8)`) → `max: 8`; most categories use `max: 8`.

**`commonListingFields`:** the seed defines a module-level `commonListingFields` const — the 11-field set photos(max 8)/title(req)/price(req)/discount/description/location/address/deliveryFree/contactName/contactPhones(max 3)/contactEmail (the camera form minus any Type and Condition fields). Many subcategory forms equal this set exactly (e.g. all of Pets and Foods, and the no-Type Furniture blocks like `wardrobe-and-cabinets`). **By current convention these are written out INLINE**, field-for-field, matching the existing blocks — do **not** write `fieldSchema: commonListingFields`. No block references the const as a whole `fieldSchema` value; it is only ever spread for the photos field via `...commonListingFields.filter((f) => f.key === 'photos')`. (A spec-detail spec that recommends the bare const reference is wrong about the convention — verified this way in the Pets/Foods ships. Collapsing the inline duplication into a shared reference is a tracked follow-up; see Known gaps.)

**Seed (`src/db/seed.ts`):** runs geography → categories → brands → models → attributes → admin → reports → subscriptions → **product spec pages** → **demo catalogue** → **listing photos** in order. All seeds are idempotent; models + attributes are insert-only (never overwrite admin edits). The demo catalogue (`listings/seeds/catalog-listings.ts` + `demo-people.ts`) upserts ~124 curated Khmer-market listings (about 64 cars, 41 phones, the rest across other categories) owned by **30 real person accounts** — not the admin — spread so nobody exceeds the free-plan caps; it also seeds 32 published product spec pages (21 car models, 12 phone models) and attaches photos from a checked-in cache/credits file (`db:fetch-photos` refreshes it). `listings.seed.ts` still deletes its known cars-era junk titles and removes the old admin-owned copies. Never run the full seed on production: apply targeted `UPDATE`s for form/spec changes (see Known gaps).

### Users schema

The `users` table relates to **seven satellite tables**:

| Table                   | Purpose                                                                 |
| ----------------------- | ----------------------------------------------------------------------- |
| `user_phones`           | Phone numbers (`phone unique`, `isPrimary`, owned by `userId`)          |
| `user_auth_providers`   | One row per (user, provider): `telegram`, `phone`, `google`, `facebook` |
| `user_blocks`           | Directional blocks; unique `(blocker_id, blocked_id)`, both FKs cascade |
| `user_username_history` | Handles a user released on rename; FK cascade, unique normalized handle |
| `provinces`             | 25 Cambodian provinces (slug unique, seeded)                            |
| `districts`             | 208 districts; unique on `(province_id, slug)` (fully seeded)           |
| `communes`              | 1,652 communes; unique on `(district_id, slug)` (fully seeded)          |

Key columns on `users`:

- `username / primaryPhone / email` — unique via **partial unique indexes** (`WHERE deleted_at IS NULL`), so soft-deleted users release their identifiers for re-registration. Upserts targeting these columns must pass `targetWhere: isNull(users.deletedAt)` (see `mirrorSupabaseUser`), and single-row lookups must filter `isNull(users.deletedAt)`. The username index is an **expression index on `lower(username)`** (2026-11-19), so `SokDara` and `sokdara` cannot coexist even though admin-created handles keep their typed casing; `ON CONFLICT (username)` no longer matches the expression index, so the admin seed does an explicit case-insensitive select-then-update/insert. Username generation lives in `src/users/username.util.ts` — `buildUsernameBase(first,last)` NFC-composes each name, turns internal whitespace into `-`, strips characters outside letters/marks/numbers/`. _ -`, joins the parts with `-`, and caps at 50 code points; `generateUniqueUsername(db,base)` probes `lower(username) = candidate`, suffixes `-2, -3, …`, and checks ALL rows including soft-deleted (stricter than the partial index). Wired into: Telegram login insert, `updateProfile` lazy backfill (only while `username === null`), and phone-OTP registration. Existing accounts are **not** renamed by the 2026-11-19 change. Check-then-insert → a 23505 race is possible (see Known gaps).
- `provinceId / districtId / communeId` — nullable FKs to the geo lookup tables, **`ON DELETE RESTRICT`** since 2026-09-12 (a user's location must never be silently cleared by a geography re-seed)
- `deletedAt timestamp` — soft-delete; `status='deleted'` + `deletedAt=now()`
- `preferredLanguage default('en').notNull()` — also drives the admin UI locale (the `/wanderer/*` surface reads it via an `admin_locale` cookie seeded at login; the in-dashboard `LocaleSwitcher` writes back via `PATCH /users/me`). DTO allowlist: `en, km`.

`user_phones` enforces at most one `isPrimary` row per user via a partial unique index (`user_phones_user_primary_uq`). `user_phones.phone` stays globally unique (not freed by soft-delete).

**Phone management endpoints** (all require JWT): `POST /api/v1/users/me/phones`, `DELETE /api/v1/users/me/phones/:phoneId`, `PATCH /api/v1/users/me/phones/:phoneId/primary`. Ownership is enforced via `and(eq(id), eq(userId))`.

**Block endpoints** (all require JWT): `GET/POST /api/v1/users/me/blocks`, `DELETE /api/v1/users/me/blocks/:userId`. Blocking is idempotent (`onConflictDoNothing`); a block in either direction makes chat sends fail with 403 (see Chat).

**Follow endpoints** (2026-09-28): `GET /api/v1/users/by-username/:username` (**`@Public()`** — returns the explicit `PublicProfile` allow-list: identity, `createdAt`, `isVerified`, both counts; never phone, email, role or moderation state; **lookup is case-insensitive and, when no account holds the handle, resolves `user_username_history` so a released handle returns the current owner's profile — clients compare `username` to the requested slug and `308` to the canonical URL**), `GET/POST/DELETE /api/v1/users/:id/follow` (JWT — read status / follow / unfollow), `GET /api/v1/users/:id/followers` and `/:id/following` (JWT, offset-paginated via `ListFollowsDto`, every row carrying viewer-relative `isFollowing`), and `GET /api/v1/users/me/follow-counts` (JWT). Backed by **`user_follows`**, which mirrors `user_blocks` exactly — unique pair index + reverse index + `follower_id <> following_id` CHECK, both FKs `CASCADE` so `AccountPurgeService` keeps working (it hard-deletes `users` rows and depends on every inbound FK taking its rows along). **Follow and unfollow are both idempotent**: `POST` rides `onConflictDoNothing`, and `DELETE` deliberately does _not_ 404 on a missing edge (unlike `unblockUser`) because the control is a toggle whose end state is the whole contract — a double-tap must land on "not following", not an error. Following is refused with **403** when _either_ side has blocked the other (`isBlockedEitherWay`, reused from `chat/blocks.util.ts`), and a genuinely **new** edge writes one `follow.created` notification — the `returning()` row gates it, so a replay cannot double-notify. **The follower lists require a JWT on purpose:** that is what lets each row carry `isFollowing` without an N+1, and it is the one place this feature diverges from the rest of the read surface; the profile endpoint itself stays public. Nothing here is transactional with the notification — see Known gaps.

**User search (2026-11-09):** `GET /api/v1/users/search?q=&page=&pageSize=` is `@Public()` and throttled at 30/min/IP. It searches only active, non-deleted, non-staff (`role = 'user'`) users with a username; whitespace tokens are prefix-matched case-insensitively (escaped `ILIKE` with a trailing `%` only, so `%`/`_` stay literal) across `username`, `first_name` and `last_name`, and the response is the allow-list `{id, username, firstName, lastName, profilePhotoUrl, verifiedAccount}` with offset pagination (`page` ≤ 100; `pageSize` ≤ 50, default 20; `q` 1–100 chars). `verifiedAccount` is the active-paid-subscription `EXISTS`; the correlated column is table-qualified, because Drizzle renders a single-table select's columns unqualified. No phone, email, role value, status, company or verification timestamp is returned; no viewer block filtering (the route is anonymous and viewer-agnostic, like `by-username`). Declared before `@Get(':id')` so `search` is not captured by `ParseUUIDPipe`.

**Activity tracking:** `LastSeenInterceptor` (global `APP_INTERCEPTOR`) calls `ActivityService.touch(userId)` on every authenticated request, and the chat gateway also calls it on every socket pong, so an open socket counts as activity. `touch` is fire-and-forget with a 60 s in-memory throttle per user — below the BFF's 2-minute online window. The exact timestamp is staff-only on the admin surfaces and participant-only in chat: `getConversationWith` returns `lastSeenAt` only when a conversation exists, and job-application summaries keep their existing relationship-scoped field.

### Brands

`BrandsModule` (`src/brands/`) — lookup tables for brand/model selects on listing forms.

```
GET /api/v1/brands                        → all active brands, sorted by sort_order
GET /api/v1/brands?subcategory=<slug>     → brands linked to that subcategory ([] if slug unknown)
GET /api/v1/brands/:id/models             → active models for a brand ([] if none)
GET /api/v1/brands/:id/models?subcategory=<slug>  → only the models in that subcategory
```

**Models are scoped to subcategories (2026-09-22).** `models` is keyed by `(brand_id, slug)` alone, so it could not tell an iPad from an iPhone and `?subcategory=` did not exist — Tablets under Apple listed iPhones, and Xiaomi's phones showed under Cars For Sale. The dimension lives in a fourth table, **`model_subcategory_links`** (mirroring `brand_subcategory_links`, same shape and cascade), because a model may genuinely span two subcategories (Surface Pro is a tablet and a laptop).

**The filter rule:** with no `subcategory` param the brand's whole catalogue comes back (the admin Models page uses this). With one, the result is **models linked to that subcategory, plus models with no link at all** — an unclassified or admin-created model must never silently empty a picker, the same managed/global philosophy as `forSub`. A model linked only _elsewhere_ is excluded, which is the actual fix. Note the naive test (`subcategoryId != <this>`) would be wrong: it would drop a model linked to two subcategories from both, which is the case the link table exists for — `BrandsService.listModels` uses `inArray(linkedToThis) OR notInArray(linkedAnywhere)`.

All three routes are `@Public()`. Four DB tables: `brands`, `models`, `brand_subcategory_links` and `model_subcategory_links` (junctions). `MODEL_SEEDS` / `MOTO_MODEL_SEEDS` in `brands.seed.ts` are **grouped by subcategory** (`Record<brandSlug, Record<subcategorySlug, string[]>>`) — that grouping IS the classification, and `seedModels` seeds the links in a second pass, which is what makes it apply to the ~385 model rows that already existed (models are insert-only, so only the links are new). The motorcycle list stays flat and is wrapped at the call site, since every moto model is `motorcycles-for-sale`. **Model slugs spell `+` as `-plus`** (`slugify` in `seedModels`). A trailing `+` is meaningful — "Galaxy S25+" is a different phone from "Galaxy S25" — but `+` is outside the admin DTO's `SLUG_RE` charset. Until 2026-09-22 both slugified to `galaxy-s25`, and since the seed lists the `+` entry **first**, it won the slug and the **plain** Galaxy S21…S25 were silently dropped by `onConflictDoNothing` — the database was missing the base models, not the plus ones. Migration `0020_fix_plus_model_slugs` renamed the six rows that had already claimed a bare slug (`galaxy-s21`…`galaxy-s25`, `realme-12-pro`); it is a no-op on a fresh database. **`seedModels` now guards against the class of bug** via `findSlugCollisions` (`brands.seed.ts` — a pure exported function with unit tests in `brands.seed.spec.ts`): `onConflictDoNothing` discards a colliding model silently, so after the insert pass it compares each seeded name against the name stored at that `(brandId, slug)` and warns when they differ. Comparing **names** is what separates a real collision from an ordinary idempotent re-run, where every model "conflicts" because it is already there — a guard that warned on every conflict would be noise on every seed. The summary line counts collisions when there are any. Verified firing end-to-end 2026-09-22 by temporarily seeding a colliding name (`'iPhone 16*'`, which slugifies onto the existing `iphone-16`) — a method that needs no database mutation, so an interrupted run leaves nothing behind. **Nothing else in the codebase writes a model row** — `admin-models.service.ts:122` (admin `PATCH /admin/models/:id`) is the only writer; there are no triggers on `models`, no `pg_cron`, and the seed is insert-only. Assigning a model to a subcategory its brand is not linked to is **refused with a warning rather than written** — such a model could never be reached there; the seeded models left out for that reason are listed in a comment block above `MODEL_SEEDS` (ASUS's phones, Canon's camera bodies, Panasonic's Lumix, Philips's monitors, Vertu…). **Surface Pro 10 is the live multi-link case** — it carries both `laptops` and `tablets`, which is the whole reason this is a junction table rather than a column on `models`. (Microsoft was linked to `tablets` on 2026-09-22 for exactly this; before that the guard refused the link.) The seed (`brands.seed.ts`) has two sets: `BRANDS` — 65 brands covering phones, tablets, smart-watches, and computers-and-accessories subcategories — plus `CAR_BRANDS` — 91 car brands (cars-and-vehicles → cars-for-sale), names/order taken from the web mock design (MG first), slug + icon derived from the app's local `/sub-img/car_vehicles/cars-for-sale/brands/*.png` design assets (interim icon source until these move to Supabase Storage; admins replace via the UI). `BrandSeed.icon?` lands only on INSERT — the brand `onConflictDoUpdate.set` never touches `icon`, so admin-uploaded icons survive re-seeds. A slug appearing in two sets is handled specially: the first occurrence upserts the row, later ones only wire `brand_subcategory_links` (+ null-icon backfill) so they can't clobber the earlier set's `sortOrder` (the one case: `xiaomi`, in both phones and cars; its car-grid position follows the phone order).

**`MOTO_BRANDS` (third set, 2026-08-31):** 31 motorcycle brands (`cars-and-vehicles → motorcycles-for-sale`), design order from the web mock (Honda first). Slugs derive from the asset filenames — the mock's `royal-enfeild`/`others` entries map to `royal-enfield.png`/`other.png`; names are mock-verbatim (including the "Royal Enfeild" spelling). Honda/Suzuki/BMW also appear in the cars set with a DIFFERENT logo asset: the moto entries take `-moto` slugs (`honda-moto`, `suzuki-moto`, `bmw-moto`) so each branch keeps its own row, icon, and design position (both grids render the same display name). The moto `other` row is the phones-family Other (sortOrder 999, admin-uploaded icon) shared across subcategories — the same shared-slug exception as `xiaomi`. Moto icons are the `/sub-img` assets (interim) until admins replace via the UI. `seedBrands` log counts all three sets.

`sort_order` is manually assigned — not auto-increment. `Other` always gets `sortOrder: 999` (phones set; the car set's `other-car-brand` is simply last in the design order). The `models` table is seeded with ~250 starter models (`MODEL_SEEDS` + `seedModels` in `brands.seed.ts`, insert-only) covering the major phone/laptop/printer/smartwatch brands plus car models for the design's model-bearing brands (mg/leapmotor/toyota — the mock's "Pirus" typo is seeded verbatim); admins add the rest via the admin Models page (each model carries an optional image; old images are cleaned up on update/delete via `removeByPublicUrl`). The brands list response shape is `{id, slug, name, icon, sortOrder}` — the field is `icon`, not `image` (models use `image`); brands do NOT nest models (`GET /brands/:id/models` is a separate call).

### Listings

`ListingsModule` (`src/listings/`) — marketplace listings with cursor-based public feed and offset-based owner feed.

**Feed (`GET /api/v1/listings`):** `findFeed()` resolves slugs via a private `resolveQueryFilters`; any unknown slug short-circuits to `{ data: [], meta }` — no error (same in `findMine`). Params: `categorySlug`, `subcategorySlug`, `provinceSlug`, `districtSlug`, `communeSlug`, `q`, `minPrice`, `maxPrice`, `condition`, `yearMin`/`yearMax` (`attributes->>'year'`; non-numeric never match), `engineType`, `sort`, `postedWithin`, `deliveryFree`, `userId` (one seller's active ads), `includeTotal`, `includeFacets`, `brand`, `bodyType`, `model`, `taxType`, `color`, `transmission`, `attrKey`+`attrValue`, and `attrs` (a JSON object of attribute-key→value pairs, AND-ed). `districtSlug` without `provinceSlug` (and `communeSlug` without `districtSlug`) is silently ignored; half an `attrKey`/`attrValue` pair applies nothing, as do malformed or oversized `attrs`. `brand`/`bodyType`/`model`/`taxType`/`color`/`transmission`/`attrKey` match the display names stored in the `attributes` JSONB; `attrKey` is validated to a plain identifier and **bound as a parameter, never interpolated** (unit tests compile the WHERE and assert `->>$n`).

**Search, sort and facets (2026-10-05):** `q` is a real keyword search — ≤ 5 whitespace tokens, every token must appear in `title` or `description`; an empty first page retries through `word_similarity` trigram matching (tokens of 4+ chars only), a mode pinned in the cursor (`f`) and reported as `meta.fuzzy`. `minPrice`/`maxPrice` bound the generated `STORED` `effective_price` column (post-discount), so NULL-price "Negotiable" listings are excluded while a bound is set. `sort` ∈ `newest | price_asc | price_desc | relevance` (relevance ranks by `word_similarity`, falling back to newest without `q`); `postedWithin` ∈ `today | week | month` (ICT); `includeTotal`/`includeFacets` add `meta.total` / per-category (then per-subcategory) counts.

**Trending (`GET /api/v1/listings/trending`, 2026-10-26):** engagement-ranked over a rolling window (default 7 days, max 30; `limit` default 10, max 20): weighted `listing_events` (view 1, chat/call/show_contact 3, apply_job 5 — **impressions excluded**) plus likes/saves at 2 each with the owner's own excluded, live listings only; the tail is filled with the newest live listings. Single page, no cursor (the score moves as events land), 5-minute per-process cache.

**Nearby (`GET /api/v1/listings/nearby`, 2026-11-10):** the mobile home card's location read. Params: required `lat`/`lng` (finite and in range; blank query values are rejected rather than coerced to 0), `radiusKm` 1–50 (default 10), `limit` 1–24 (default 8); any other param is a 400. Returns `{ data, meta: { limit, radiusKm } }` — live listings only (`active`, not past expiry) whose owner is `active`, with both coordinates set, inside a latitude/longitude bounding box and within the exact Haversine radius (`numeric` cast to `float8`), ordered by distance then id, with photos and the same card projection as the feed/trending. No cursor, no total, no cache: the feed's keyset cursor carries only `{s,v,id,f}`, so a later page fetched from a different origin would reorder or skip rows, and an exact-coordinate cache key would hold the caller's position in process memory. `nearby.ts` owns the distance SQL and box helper; the box is deliberately a superset of the circle (111.0 km per degree) and is dropped when it crosses the antimeridian. The route is `@Public()` with a 30/min throttle; `lat`/`lng` values are redacted from every log line (request logger and exception filter). Listings without a pin are absent by design — there is no province fallback.

**Ad creation** — `POST /api/v1/listings` (JWT): takes `categoryId`/`subcategoryId` as **UUIDs** (not slugs), inserts with `status='draft'`, `attributes` JSONB, `photos: [{url, path, sort}]` (max 8 — `url` = Supabase public URL, `path` = the `/files/sign` storage path; no upload tokens). `POST /api/v1/listings/:id/publish` (owner) flips to `status='active'` + `expiresAt = +30d`; the feed only shows `active` — a client post flow must call create **then** publish. The plan allowance (pool total + scope cap) is checked at create as well. Update/PATCH swaps `listing_photos` rows and best-effort cleans up dropped photos after commit.

**Cursor (feed):** sort-aware base64 JSON `{ s, v, id, f? }` (sort, last sort value as TEXT, fuzzy flag); a cursor from one sort is ignored on another. Sort values round-trip as text (`created_at::text`, `effective_price::text`), never JS Dates (ms truncation would skip boundary rows). Invalid cursors are ignored; the legacy `{createdAt, id}` shape still pages old links.

**Moderation and expiry:** approving a listing report (or `/admin/listings/:id/remove`) sets `status='deleted'` + `moderated_at` + `deleted_at`; the feed and public detail hide it and publish refuses with `LISTING_REMOVED_BY_ADMIN`. Both the direct remove and the report-approval path notify the owner (`listing.removed`, with the reason). A staff removal is **terminal**: `restoreModerated` refuses a stamped row, so `inactive` is the only undoable staff state. The client surfaces (web Manage Ads, mobile) must therefore hide any restore affordance, and the admin delete action should confirm.

**Delete vs `inactive` (2026-11-08):** the two staff outcomes are now different in kind, and neither removes a row. `delete` — the owner's `DELETE /listings/:id` and the admin's `remove` — stamps `listings.deletedAt`, which nothing clears: `publish` refuses with `LISTING_DELETED_PERMANENTLY` and the restore paths refuse the row. `inactive` stays the staff-only, reversible hide (set by `/admin/listings/:id/inactivate`, lifted only by `restoreInactive`); the owner may no longer republish a staff-hidden ad, and `publish` answers `LISTING_INACTIVE_BY_STAFF`. Keeping both rows in place is deliberate — a real `DELETE` would cascade the ad's `listing_reports` away and retroactively lower the approved-report count the account threshold reads. **Rows deleted or removed before migration `0056` are grandfathered**: the marker is not backfilled, so a pre-existing `status='deleted'` row with no `deletedAt` is still republishable by its owner and still restorable by staff. A backfill (`UPDATE listings SET deleted_at = … WHERE status='deleted' AND deleted_at IS NULL`) is a deliberate data write that has not been run.

**A suspended seller's ads are hidden by a read rule**, not by a write: the public feed, public detail, trending, and the liked/saved lists exclude listings whose owner is not `active`, and reinstating the account makes them visible again with no data change and no second notification. The predicate lives in the feed's shared condition set, so the page rows, the `total` count and the facet counts all apply it — each of those queries joins `users`. Two deliberate exceptions: a listing card embedded in chat history (`batchLoadListingContexts`) keeps rendering (the conversation must stay readable), and the owner's own `/me/all` always lists their ads.

**Expiry is derived, never stored:** `findPublicById` reports a lapsed `active` ad as `expired` (its shared link keeps working, with contact disabled) and 404s draft/deleted; `findMine` derives the same status and maps the `active`/`expired` filters to date ranges. The hourly `ListingExpiryService` sweep sends `listing.expiring` at T-3 days and `listing.expired` once for lapses in the last 24 h.

**Owner listing** (`GET /api/v1/listings/me/all`): offset pagination + a `status` filter.

### Likes & Saved (`src/reactions/`, 2026-10-05)

`ReactionsModule` (`src/reactions/`) owns the two edge tables behind every heart and bookmark: **`listing_likes` + `listing_saves`** (`db/schema/reactions.schema.ts`, migration `0028_acoustic_chat`) — mirroring `user_follows` (unique pair index, reverse `listing_id` index, both FKs CASCADE so `AccountPurgeService` keeps working). No self-check: liking your own listing is allowed.

```
POST|DELETE /api/v1/listings/:listingId/like   → { liked, likeCount }
POST|DELETE /api/v1/listings/:listingId/save   → { saved }
GET  /api/v1/users/me/likes|saves              → paginated listing rows (the feed's shape)
GET  /api/v1/users/me/reactions                → { liked: uuid[], saved: uuid[] }
```

Toggles are **idempotent both ways**: `POST` rides `onConflictDoNothing`, and `DELETE` never 404s at all (the toggle's end state is the whole contract, same as unfollow — a stale unlike of a hard-deleted listing returns `{liked:false}`). The only 404 is a missing listing row **on the POST side** — mirroring `findById`, which serves **any status**, so a control that renders on the detail page is never present-but-refused. The list reads filter `status != 'deleted'` (a removed ad leaves "my likes"; the edge survives a restore); the id-set read is unfiltered (it only lights up rendered cards). `likeCount` is computed per read (no counter column) and rides the listing detail response and every like-toggle response, so the detail's "N Likes" never refetches; `ListingsModule` imports `ReactionsModule` (no cycle).

**Web side:** the `(user)` layout reads both id sets once per signed-in render (fail-soft to empty) and wraps the tree in `components/reactions/reactions-provider.tsx`; `useReactions()` is the single source for every control (grid + list hearts, the ⋮ Save/Unsave — the menu stays open — the detail row's Save, and the detail's "N Likes" + count). Toggles are optimistic with rollback-toast, disable while pending (per listing, either kind), bounce visitors to `/login` with a "Sign in to like/save" toast, and ignore non-UUID (mock) ids entirely — a demo heart is inert, never a request or an error toast. A row toggled off mid-session drops out of the `/me` lists live (`isToggledOff`, not membership — the seed sets fail soft). `/me/likes` + `/me/saved` render the real listings via `components/profile/reaction-ads-panel.tsx` (loading/error/empty distinct — an empty list and a failed one must not look the same — plus "Load more"; the existing "No Result!" empty designs are kept). Not included: notifications on like/save; admin surfaces; counts anywhere but the detail control.

### Chat

`ChatModule` (`src/chat/`) — 1:1 buyer↔seller messaging. **REST is authoritative; a WebSocket gateway is an optional low-latency push on top, not a replacement.** Every message — REST or WS — goes through the single `ChatService.sendMessage` write path, so validation exists once. Its three pre-write checks (recipient existence, block check, listing ownership) run concurrently via `Promise.all` rather than sequentially — each is an independent read, and each DB round trip is real latency against the remote Supabase pooler, so this is the difference between one queueing round trip and three under concurrent send load. See `DATABASE_POOL_MAX` above: the shared postgres.js pool (default 20, not chat-specific) is the actual scaling limit under concurrent chat traffic, not `ConnectionRegistry` (verified empirically — 20 concurrent WS sends across 2 connections showed 0 drops/duplicates/misrouting; latency scaled with pool contention instead). **Per-contact threads**: exactly one `conversations` row per unordered user pair (CHECK `user_a_id < user_b_id` + unique; the service canonicalizes the pair and upserts with `onConflictDoUpdate`, bumping `last_message_at`). A message may carry an optional `listingId` context card (FK `ON DELETE SET NULL`). All routes require JWT. Full design + diagrams: `src/chat/README.md`.

```
POST /api/v1/chats/messages          → send { recipientId, body, listingId?, e2eHeader? | e2e?, attachmentIds? } — E2E required; find-or-creates the conversation
GET  /api/v1/chats                   → inbox: cursor on (lastMessageAt, id); items carry otherUser, lastMessage, unreadCount
GET  /api/v1/chats/unread-count      → { total } for the badge
GET  /api/v1/chats/with/:userId      → resolve thread with a user (read-only — never creates; conversation may be null)
GET  /api/v1/chats/:id/messages      → history (cursor=, DESC) or polling deltas (after=, ASC); meta adds latestCursor + peerLastReadAt
POST /api/v1/chats/:id/read          → bulk mark-read; returns { marked }
```

Send rejections: self (400), missing E2E envelope (400 `Encrypted messages are required`), empty body (400), any `imagePath` (400 `Unencrypted chat images are not accepted` — the legacy public imagePath is rejected for new sends), recipient missing/soft-deleted (404), block in either direction (403 `Messaging unavailable`), listing owned by neither participant (400). Non-participants get 404 (not 403) on conversation routes — no existence oracle. Clients poll with `after = meta.latestCursor`; read receipts surface via `peerLastReadAt` (= `max(readAt)` of my messages, valid because mark-read is bulk).

`messages.created_at` and `conversations.last_message_at` are `timestamp(3)` — cursor values roundtrip through JS Dates (ms precision), so µs columns would re-deliver the boundary row on `after` polls.

**WebSocket gateway** (`chat.gateway.ts`, `/ws/chat`): authenticates with the 60 s ticket (`?ticket=` or `Authorization: Bearer`, `typ: 'ws'` only — a full access token is never accepted) and rejects a browser `Origin` not in `FRONTEND_ORIGINS`, then runs the same soft-delete **and `tokensValidAfter`** DB check `JwtStrategy.validate` does on the REST path (parity — a soft-deleted user or a password reset ends the socket). `send_message` is rate-limited in-memory, 30/min per user, mirroring the REST route's `@Throttle`; its payload is validated in the handler with the REST `ValidationPipe` options (the envelope is an interface, so the global pipe can't see it), and every send is answered with exactly one frame echoing `clientMessageId` — `ack` `{conversationId, message}` or `error` `{code, message, details?}` with the same codes as the REST error envelope (errors are caught in the handler because `GlobalExceptionFilter` is HTTP-only). `markRead` pushes a `read` `{conversationId}` event to the other participant so a WS-connected sender's receipts update live (their delta poll is paused while the socket is up). `ConnectionRegistry` is still an in-memory per-process `userId -> sockets` map — a given instance can only write to its own local sockets — but `ChatPubSubService` (`chat-pubsub.service.ts`) now publishes every push (`message`, `inbox_update`, `unread_count`) over Redis pub/sub (reusing the BullMQ Redis connection), so every instance's gateway subscribes and delivers to its own locally-connected recipient. Real-time push therefore reaches a recipient on _any_ backend instance, not just the sender's; an offline recipient still gets the message via their next `after=` poll, so correctness never depends on the socket. `HeartbeatService` pings every open socket every 30s and evicts any that hasn't ponged in 40s. On the web client, `use-chat-ws.ts` holds one shared WebSocket per tab (ref-counted across the nav unread badge, inbox list, and any open thread) and `inbox_update`/`unread_count` pushes replace the flat-interval inbox/badge poll whenever that socket is connected — see `CHAT_POLL` in `use-chat-polling.ts` for the fallback tiers used the rest of the time.

**End-to-end encryption** (X3DH + Double Ratchet over `@noble/curves`, Signal-protocol shaped): `SendMessageDto.e2eHeader` (validated by `E2eHeaderDto`) marks a message as E2E — `body` becomes base64 ciphertext (max 24000 chars vs. plaintext), mutually exclusive with `e2e`; the legacy `imagePath` is rejected outright, and media (images, voice notes) travels as encrypted v2 attachments. The header carries the Double Ratchet fields (`dh`, `pn`, `n`) plus, only on a session's first message, the X3DH initial-message fields (`identityKey`, `ephemeralKey`, `oneTimePrekeyId`, `signedPrekeyId`). Stored verbatim in `messages.e2eHeader` (JSONB) alongside `messages.isE2e`. Key material lives in two tables: `user_e2e_identities` (one row per user — X25519 `identityKey` for DH, a **separate** Ed25519 `identitySigningKey` for signing `signedPrekeyPublic`, since `@noble/curves` doesn't expose the Edwards↔Montgomery conversion Signal's XEdDSA uses to make one key do both) and `user_e2e_one_time_prekeys` (claimed one at a time via a partial index on unused rows). `E2eKeysController` (`/api/v1/chats/e2e/keys`): `POST` registers/rotates a user's keys + replenishes one-time prekeys, `GET me/prekey-count` reports remaining stock, `GET :userId/bundle` fetches a peer's bundle (identity key, signing key, signed prekey + signature, one claimed one-time prekey) to start an X3DH session. The backend only stores and relays key material and ciphertext — it never sees plaintext or private keys. **v2 multi-device** (`e2eVersion=2`): one identity per browser (`user_e2e_devices`), the message key wrapped per recipient/sender device in `message_envelopes`; a stale device list → 409 `E2E_DEVICES_MISMATCH` with `details` for the client to fix and retry. **History backup** (`e2e-backup.*`, `/chats/e2e/backup`): a per-account backup key (BK) encrypts plaintext segments; a new device gets BK only via the account passcode (argon2id → server-rate-limited unlock); device approval was removed on 2026-10-26, and `0041_brainy_plazm` drops `chat.e2e_history_requests`. Plan + status: `tasks/plan-e2e-multi-device.md`; open security items: `src/chat/README.md`. **Encrypted attachments** (`chat-attachments.*`, `/chats/attachments`, design `docs/e2e-attachments.md`): the browser resizes images to WebP, encrypts each file with its own AES-256-GCM key (frozen `E2E_FILE_V1` format: `NPF`+version, IV, ciphertext+tag) and uploads ciphertext to the **private** `chat-files` bucket (octet-stream only, 25 MB cap); keys, MIME types and thumbnails ride inside the v2 E2E message. `chat.attachments` tracks `pending → uploaded → attached`; `complete` trusts only the size read from storage; `POST /chats/messages` attaches `attachmentIds` in the send transaction with one conditional `UPDATE`; downloads use 5-min signed URLs issued only to participants; integrity is recipient-verified (hash + GCM tag), so there's no server-side hash. An hourly BullMQ job (`chat-maintenance` queue) deletes objects + rows never attached within 24 h. Legacy `imageUrl`/`imagePath` rows stay in the public bucket and still render; `NEXT_PUBLIC_E2E_ATTACHMENTS=off` is now a kill switch that disables encrypted media (images, voice notes) entirely — there is no plaintext fallback, so media fails closed.

### Files

`FilesModule` (`src/files/`) handles file uploads to Supabase Storage. Signed upload URLs are generated server-side; the client uploads directly to Supabase. Public URLs are returned for confirmed uploads. Bucket name is configured via `SUPABASE_STORAGE_BUCKET` (default: `listings`). Bucket limits and the client upload contract are owned by `apps/backend/src/files/README.md`.

**Upload scopes** (`POST /files/sign`, `SignUploadDto.scope`): `avatar | cover | listing | chat | category | subcategory | brand | model | attribute` — `chat` paths are per-user (`chat/{userId}/…`); the scope is now legacy — the web no longer signs chat uploads, since new sends reject `imagePath`. `DELETE /files` takes `{ paths: string[] }` for path-based deletion.

**Image cleanup on replace/delete:** `FilesService.removeByPublicUrl(publicUrl)` (`files.service.ts:105-125`) derives the storage path from a public URL, silently skips non-storage values (`/placeholder.svg`, foreign URLs), and warns-but-never-throws. The established pattern: read the prior `image`/`icon` inside the DB op, call `removeByPublicUrl(old)` **after commit**, gated on the value actually changing. Currently wired for: attributes, brands, models, categories/subcategories (icons), user avatar, user cover, and listing photos (removed-from-payload diff). **Not** wired for: admin user soft-delete (avatar/cover stay live in storage), chat images (no message-delete endpoint exists by design), and listing soft-delete (restore must work).

### Payments

`PaymentModule` (`src/payment/`) — gateway-agnostic payment processing feeding a double-entry ledger; the full design (table layout, entity map, outbox/queue placement, lifecycle sequence, current status) lives in [`src/payment/README.md`](apps/backend/src/payment/README.md), the canonical Module README example. **Background work on a scale-to-zero host:** `PaymentReconciler` is the only poller (Bakong has no webhook), and while an instance is warm it is armed by `payment.issued` and settles from Postgres. Because the Vercel container scales to zero, an authenticated `POST /internal/payments/reconcile` (header `x-internal-secret`, `INTERNAL_RECONCILE_SECRET`) runs one deduplicated pass for an external pinger/cron; it deliberately does not depend on `PAYMENT_RECONCILER_ENABLED`, which only turns off the in-process timer. One thing that README won't flag because it's a backend-wide convention question, not a module detail: **this module's use-cases are written in [Effect](https://effect.website) (`effect` npm package), not plain async/await NestJS services.** `use-cases/**/*.use-case.ts` (split into `use-cases/payments/` — payment_transaction/payment_attempt/provider-event lifecycle — and `use-cases/ledgers/` — double-entry posting, mirroring the processing/ledger table split; the top-level `use-cases/index.ts` re-exports both so every consumer still imports from one place) are `Effect.fn`-wrapped generators that `yield*` a `DbClientTag` (`src/db/db.provider.ts` — an Effect `Context.Service` wrapping the same Drizzle client the `DRIZZLE` token provides everywhere else) and fail with `Schema.TaggedError` subclasses (`use-cases/payments/errors.ts` / `use-cases/ledgers/errors.ts`) instead of throwing. `PaymentsController` is the only bridge back to NestJS: its private `run()` helper provides `DbClientTag.layer(this.db)`, runs the effect with `Effect.runPromiseExit`, and maps a typed failure to an `HttpException` via a `switch` on `error._tag`; an unmodeled defect falls through to `GlobalExceptionFilter` as a 500. This pattern is currently unique to `payment/` — don't reach for `effect` in other modules without a deliberate decision to extend the convention.

### Adding a new feature module

1. Create `src/<feature>/{feature}.module.ts`, `.service.ts`, `.controller.ts`.
2. Add DTOs to `src/<feature>/dto/`.
3. Import the module in `AppModule`.
4. Mark public endpoints with `@Public()`. Everything else requires a valid JWT automatically.
5. Do **not** import `DbModule` or `SupabaseModule`; their providers are available globally.

**For admin-only features**, add the controller + service to `AdminModule` instead of creating a separate module. Register them in `src/admin/admin.module.ts`. The controller uses `@Roles('admin', 'super_admin')` (guard is inherited from `AdminModule` or applied at the controller level if the feature has its own module).

**Exception:** the attributes feature owns its own module at `src/attributes/` (`AttributesModule` — admin-scoped routes at `/admin/attributes/:type`, registered in `AppModule`, imports `FilesModule`). It was decoupled from `AdminModule` so it can grow a public surface; keep admin-only features in `AdminModule` unless they have the same trajectory.

### Notifications

`NotificationsModule` (`src/notifications/`) — the user-facing notification feed, plus the SMS send-path behind it. Not `@Global()`: importing it is a deliberate choice (the importer now sends notifications).

```
GET    /api/v1/notifications              → offset-paginated (page/pageSize ≤ 100), newest first
GET    /api/v1/notifications/unread-count → { total }
PATCH  /api/v1/notifications/read-all
PATCH  /api/v1/notifications/:id/read
DELETE /api/v1/notifications/:id
DELETE /api/v1/notifications
```

`NotificationsService.notify()` fans a payload out over `NOTIFICATION_CHANNELS` (today: `InAppNotificationChannel` — the durable `notifications` row — and `RealtimeNotificationChannel`, a best-effort WebSocket push over the chat pub/sub). `Promise.all`, not `allSettled`, on purpose: the durable row's failure has to propagate, since the caller is usually an `OutboxHandler` whose own retry is what re-fires `notify()`.

**SMS is opt-in per notification (`data.sendSms === true`) and is NOT a channel in that array — it never runs inline.** `notify()` instead enqueues a durable outbox event, `notification.sms.requested` (dedupeKey = `userId + type + a stable hash of data`, so a duplicate `notify()` call for the same logical event enqueues exactly once), and writes a matching `queued` row in `sms_deliveries`. `SmsOutboxHandler` (`src/notifications/sms/`) consumes it later, completely decoupled from the caller's own success/failure:

1. **Unconfigured** (`SMS_PRIVATE_KEY`/`SMS_SECRET`/`SMS_SENDER` not all set) → records `skipped` (`not_configured`) and reports the event `published` (terminal, not retried) — dev needs no setup.
2. **Allowed-type gate** — only `auth.phone.verify` and `auth.password.reset` (`SMS_ALLOWED_TYPES`) may be texted; any other type is `skipped` (`type_not_allowed`), so payments etc. stay in-app only until added to the list.
   2b. **Verified-phone gate** — texts only when the user's `primaryPhone` is OTP-verified (`users.phoneVerifiedAt` set); otherwise `skipped` (`phone_not_verified`), also `published`. An unparseable number is `skipped` (`invalid_phone`) the same way. `phoneVerifiedAt` is stamped by the phone-change OTP flow (`verifyPhoneChangeOtp`) and, as of this change, by the login/registration OTP flow (`AuthService.verifyPhoneOtp`) too — previously only the former wrote it, so most accounts read "Not Verified" even after proving ownership at login. Changing the primary phone WITHOUT an OTP (`addPhone`, `setPrimaryPhone`, the auto-promotion inside `removePhone`) now clears `phoneVerifiedAt`, since the column only ever means "the CURRENT `primaryPhone` was OTP-verified" and there is no per-number verification record to fall back on.
   2c. **Per-user spam limits** — `SmsUserLimiter` (Lua script on the same Redis) allows 1 SMS per user per type per `SMS_USER_COOLDOWN_SECONDS` (default 300; over it → `skipped` `rate_limited`) and `SMS_USER_DAILY_CAP` per user per day (default 10; → `skipped` `daily_cap`); no type is exempt, over-limit messages are dropped not delayed, Redis down → `retry` (fail closed). The slot is taken only after the gates above, is keyed by the outbox event id (a retry of the same event reuses it), and is released when the global limiter or PlasGate answers `retry`, so a retry never burns the cooldown.
3. **Rate limiter** (`SmsRateLimiter`) — a Redis-backed sliding window (same `QUEUE_*` connection family as `ChatPubSubService`'s pub/sub), budget `SMS_RATE_LIMIT_PER_MINUTE` (default 150, under PlasGate's own 200/minute ceiling), shared across every backend instance. Over budget, or Redis itself unreachable, both answer the handler's own `retry` — **fails closed**, never silently sending past the budget.
4. **PlasGateClient** (`POST {SMS_BASE_URL}?private_key=…`, header `X-Secret`, body `{sender,to,content}`) classifies the HTTP outcome: 2xx → `sent`; network error/timeout/429/5xx → `retry`; any other 4xx (bad sender id, bad number) → permanent `failed`. Neither the private key nor the secret is ever logged.

Every attempt outcome updates the matching `sms_deliveries` row (migration `0050`, keyed 1:1 on `outboxEventId`) — `status` (`queued|sent|failed|skipped`), `skipReason`, `providerStatus`/`providerReply`, `attempts`. **No message-text column**: `SmsOutboxHandler.redact()` strips the rendered content from the outbox payload once the event reaches a terminal state, same pattern as the payment handlers' `redact()`. `notify()` queues the event and its `queued` audit row in ONE transaction (an event with no audit row would be sent with nothing recorded), and an enqueue failure is logged, not thrown, so a caller that retries on a throw never re-writes the in-app row. The in-app row `notify()` wrote is never affected by any of this — that decoupling (durable record vs. best-effort, rate-limited external send) is the entire point.

`SMS_REQUESTED_MAX_ATTEMPTS` (20, well past the outbox's global default of 5) exists because `OutboxService` increments `attempts` at **claim** time, not on completion — an over-budget `retry` burns an attempt exactly like a transient network failure would, and a burst can legitimately need several retries before a rate-limit slot frees up.

**Dashboard feed (2026-11-10).** The admin dashboard's header bell reads the signed-in staff member's own `notifications` rows through the admin session (`serverFetch`), not the report queues: `GET /notifications/unread-count` drives the badge, and the newest eight rows fill the right drawer, with one shortcut row per pending report queue. `report.created` rows link to the matching queue (user or listing), `report.threshold` to the Users page filtered to its target (`?q=…&status=…`) and `listing.edited` to the Listings page; every other type stays read-only. Clicking a row marks it read. The drawer and `/wanderer/dashboard/notifications` (offset-paginated, mark-all, delete-one, delete-all) invalidate the `["admin","notifications"]` keys. The unread poll runs every 15 s while visible and stops on a 401 (the action answers `null`); a report-queue status update also invalidates the admin notification queries immediately, so the approving admin sees a threshold notice without waiting for the poll. The page and drawer sit behind the dashboard layout/proxy. `NotificationsService.list` orders by `createdAt desc, id desc`, so staff fan-out rows inserted in the same instant cannot shift between pages.

### Job applications (`src/applications/`)

`job_applications` (migration `0036`) — one row per (listing, applicant), `pending|viewed|hired|rejected`; `poster_id` is denormalized from the listing, and `CHECK (applicant_id <> poster_id)` backs the service's 400. `POST /listings/:listingId/applications` (throttled 10/min) validates first, **sends the encrypted chat message through `ChatService.sendMessage`** (`clientMessageId = apply:<listingId>:<applicantId>`, so a retry replays), and **only then inserts the row** with `onConflictDoNothing().returning()`; a duplicate is 409 `JOB_APPLICATION_EXISTS`. ### Reports & moderation (`src/reports/`, `src/admin/reports/`)

`GET /reports/reasons?targetType=user|listing` is public; `POST /reports` (JWT, 5/min) files one **pending** report per reporter→target (409 `REPORT_ALREADY_PENDING`), validates the reason against the target type, and requires evidence paths under `report/{reporterId}/`. Admin queues: `GET/PATCH/DELETE /admin/reports/{users,listings}`. Filing a report also writes a `report.created` notification to every active admin/super-admin (no reporter identity). **Approving takes the target down in the same transaction:** a listing becomes `status='deleted'` + `moderated_at` (feed/detail hide it; publish returns 403 `LISTING_REMOVED_BY_ADMIN`) and the owner is notified after the commit; a user becomes `status='suspended'` with the reason, session revocation and login refusal described under Auth. **Rejecting never restores.** The approval no longer bans phone numbers — `banned_phones` keeps its 8 enforcement sites but loses its only writer, so it remains a registration wall (403 `PHONE_BANNED`) with no in-app way to add a number to it.

**The threshold is a triage signal, never an action (2026-11-08).** `reports.alert_threshold` (default 5, `app_settings`) is compared against the target account's approved reports — both `user_reports` against them and `listing_reports` on the listings they own, with `status='approved'` as the only truth, so re-opening or rejecting a report re-settles the count instead of leaving a counter column to desync. At or above the threshold the approval calls `notifyStaff({ type: 'report.threshold' })` after its transaction commits, and that is the whole automatic behaviour: it repeats on every approval at or above N, it has no re-arm column, and nothing is suspended, hidden or banned by it. Every consequence — suspend, delete, inactive — stays an admin decision on the Users or Listings page. Any automatic action here would make mass-reporting a free denial of service, because the only thing the schema prevents is a duplicate _open_ report per pair.

**The post threshold is a separate, post-only signal (2026-11-18).** `reports.post_alert_threshold` (default 5, `app_settings`) counts only approved `listing_reports` on the account's listings — account reports are excluded — and is evaluated after each newly approved listing report commits, including a listing already moderated through the direct admin route (the report row still becomes approved and counts). At or above the threshold the approval sends `report.threshold` with post-specific copy and `source: 'listing'` / `approvedPostReports` in `data`, repeating on every approval at or above N with no re-arm. The per-approval take-down and owner notice are unchanged; suspension remains a manual Users-page decision. Both threshold notices name the account in the body (`@handle (Name)`) and carry `targetUsername` / `targetName` / `targetStatus`, so the bell's Open link filters the Users page (`?q=…&status=…`). Owners already at/above the threshold when this shipped are covered by the one-off `db:backfill-post-thresholds` script (`--dry-run` and `--refresh` supported); it skips any owner that already has a post-threshold notice.

### Feedback (`src/feedback/`)

Public `POST /feedback` (+ `POST /feedback/attachments/sign`) accepts anonymous or signed-in submissions (`user_id` SET NULL on purge); `imagePaths` must start with `feedback/`. Admin: `GET/DELETE /admin/feedback`. Deleting a row does not delete its storage objects.

### Advertisements (`src/advertisements/`)

Superadmin-managed storefront banners (`home | all_ads | category | subcategory | listing_detail`). Public `GET /advertisements?placement=` returns active rows only as `{id, placement, imageUrl, linkUrl, altText, sortOrder}`; admin CRUD is `@Roles('super_admin')` in a standalone module so the public read can stay anonymous. The web renders a slot with `AdvertisementCarousel` (5 s autoplay, pause on hover/focus, `prefers-reduced-motion` opt-out); an empty slot renders nothing.

### Insights (`src/insights/`)

`listing_events` (`impression | view | chat | call | show_contact | apply_job`; `owner_id` denormalized; `actor_id` SET NULL). `POST /insights/events` is `@Public()` + `OptionalJwtAuthGuard` (batch ≤ 50) and throttled at 600/min — the web calls it through a Next server action, so the IP-keyed bucket is a site-wide ceiling, not a per-visitor one. Anonymous visits are recorded with a null actor, the owner's own actions are skipped, unknown listings are dropped. `GET /insights/me` returns all-time account-wide counts; `engagement = view + chat + call + show_contact + apply_job` (impressions excluded). `listings.views_count` is unused — never write it from a read.

### Product specifications (`src/products/`)

One `product_specs` row per model (`model_id` unique, cascade) holding a pinned `family` (`car | motorcycle | phone | tablet | smartwatch`), ordered `spec_groups` JSONB (`[{title, rows:[{label,value}]}]`) and `is_published`. Public `GET /products` (published only, optional family filter, prefix keyword search over brand/model names/slugs) and `GET /products/:brandSlug/:modelSlug` (404 unless published); admin CRUD under `/admin/products` — template-driven for phone/tablet/watch (`GET /admin/products/template/:family`), freeform for cars/motorcycles. `listings.product_model_id` links an ad to a page (nullable, SET NULL); create/update reject an unpublished target or a different family. Five subcategories declare the required `productSpec` key — `cars-for-sale`, `motorcycles-for-sale`, `phones`, `tablets`, `smart-watches` — so they cannot be posted until staff create the spec page (the requirement is enforced in the web form only).

### Auth flow

Admin and user auth are **split onto separate surfaces**:

**Admin (`/wanderer/*` — non-localized, no `/[locale]` prefix):**

1. `actions/admin-login.ts` (server action) calls `POST /api/v1/auth/login`, rejects unless `user.role` is `'admin'` or `'super_admin'`, then calls `setAdminSession()` to persist `accessToken` + `refreshToken` in **httpOnly cookies** (`admin_access_token` / `admin_refresh_token`). Also seeds the `admin_locale` cookie from `user.preferredLanguage`.
2. `proxy.ts` (Next.js 16 replacement for `middleware.ts`) guards `/wanderer/dashboard/**` — if no `admin_access_token` cookie, redirects to `/wanderer/login` (with `?next=`). **Cookie presence is the proxy's only check**, so it is not the real gate: `app/wanderer/dashboard/layout.tsx:19-25` calls `getCurrentUser()` and `redirect("/wanderer/login")` unless the session resolves to an `admin`/`super_admin` — "defense in depth" against a non-admin or stale token rendering the shell. A placeholder cookie therefore passes the proxy and is still bounced by the layout (verified 2026-09-15); a real admin session is required to see any dashboard page. The entire `/wanderer/*` surface bypasses next-intl entirely (never gets a locale prefix). Stray locale-prefixed wanderer URLs (e.g. `/en/wanderer/login`) are redirected to strip the locale.
3. `app/wanderer/layout.tsx` is a **second root `<html>` layout** (Next.js supports multiple root layouts when no `app/layout.tsx` exists). It reads the `admin_locale` cookie, validates it against `routing.locales`, and wraps children in `NextIntlClientProvider` with the cookie-sourced locale + directly-imported `messages/${locale}.json`. This bypasses `i18n/request.ts` (which is URL-segment based) entirely.
4. The in-dashboard `LocaleSwitcher` (`components/dashboard/locale-switcher.tsx`) calls `actions/admin-locale.ts`, which sets the `admin_locale` cookie + `PATCH /users/me { preferredLanguage }`, then `router.refresh()` re-renders the layout in the new locale.
5. `actions/logout.ts` (`adminLogout`) clears session + locale cookies and redirects to `/wanderer/login`. The dashboard's `NavUser` menu opens a confirmation `Dialog` first; Cancel and Escape/outside-click close it without touching either cookie, and only the dialog's Log out action clears the session.

**User (`/[locale]/login` — locale-prefixed):**

1. `actions/login.ts` (server action) calls `POST /api/v1/auth/login` and accepts any authenticated user (no role gate). **Phone-shaped identifiers** (`^0\d{7,9}$` — local-only; typed `+855…` or `855…` is treated as a username and fails) route instead to `requestLoginOtp` (`actions/otp.ts` → `POST /auth/otp/login`), which validates the password first, then sends the OTP and redirects to `/{locale}/otp?phone=<E.164>`.
2. **Distinct cookies:** admin and user sessions use separate httpOnly cookie pairs — `admin_access_token` / `admin_refresh_token` (admin) vs `user_access_token` / `user_refresh_token` (user). A user login cannot satisfy the proxy's admin-cookie guard, and `serverFetch` reads admin cookies only.
3. **Post-login destination is `/me`.** Both the login form (password mode) and the OTP verify success handler push `/me` — after any successful user login/register the user lands on their account page first, never the home feed.

`serverFetch<T>(path, init?)` in `lib/api/client.ts` reads the **admin** httpOnly cookie (`admin_access_token`), injects `Authorization: Bearer`, unwraps the `{success, data, meta}` envelope, and **transparently refreshes** on 401 (calls `POST /auth/refresh`, sets new cookies, retries once). On refresh failure, clears session. Throws `ApiError` on non-ok responses. **`userServerFetch<T>(path, init?)` is the user-side twin** — identical behavior but reads USER cookies (`getUserAccessToken`/`getUserRefreshToken`) and clears the user session on refresh failure; same cookie-write-during-RSC-render caveat applies. `getCurrentUser(): SessionUser | null` (`lib/auth/current-user.ts`, server-only) is the fail-soft session reader used by the `(user)` layout — anonymous fast-path (`no access or refresh token`) returns `null` with zero backend calls; any error degrades to visitor chrome. `actions/logout.ts` exposes both `adminLogout()` and `userLogout()`.

`clearAdminSession()` on 401 failure in `serverFetch` — cookie writes throw during RSC render (read-only context), which is caught and swallowed (token persists until next mutation).

The fix has two halves and both are needed: `GET /listings` gained an optional **`attrKey` + `attrValue`** pair, and the subcategory page resolves the key from the clicked option's **set type** via `SET_FIELD_KEYS`, picking the candidate the subcategory's own `field_schema` actually declares. Verified on 10 cases across 6 subcategories, cars included as the regression control.

### Theming contract

Dark mode is a **class strategy**, not a second stylesheet: `next-themes` puts `.dark` on `<html>` (`app/[locale]/layout.tsx` and `app/wanderer/layout.tsx`, both with `suppressHydrationWarning`), and `styles/globals.css` defines the light tokens in `:root` and the dark overrides in `.dark`. `@custom-variant dark (&:is(.dark *))` is the only dark switch. Do not add a parallel theme system, a second palette, or per-page `prefers-color-scheme` rules.

| Role                                  | Use                                                                                                     | Do not use                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Page / card / popover / muted surface | `bg-background`, `bg-card`, `bg-popover`, `bg-muted`, `bg-secondary`                                    | `bg-white`, `bg-gray-*`, `bg-[#fff]`, `bg-zinc-*`        |
| Body / secondary text                 | `text-foreground`, `text-muted-foreground`                                                              | `text-black`, `text-gray-*`, `text-slate-*`              |

**Fixed-white exceptions** — only these stay white in both themes: the footer QR quiet-zone pad (`components/web/Footer.tsx`), the KHQR payment card (`components/payment/KhqrCard.tsx`), photo/lightbox overlays, and designed brand marks/logo plates. ## Schema domains beyond the core

### Subscriptions (`subscriptions.schema.ts`)

The admin UI manages a three-level catalog (`subscription_categories → subscription_packages → subscription_terms`), but a subscription category is a **group** in the API and entitlement model. Each group sells at most one package per fixed tier (`bronze|silver|gold`), and each package carries fixed 3/6/12-month terms. `subscription_category_subcategories` assigns each listing subcategory to at most one group; a held subscription grants the package limits across that group's scope, while unheld/out-of-scope ads use the configured free plan.

- `subscription_packages` is unique on `(categoryId, tier)`; parent group deletion cascades through packages and terms.
- `subscription_packages` feature fields are **integers** (`photos`, `ads`, `renews`, `autoRenews`, `videos`). `autoRenews` and `videos` are stored but are not enforced by current listing features, and are no longer shown on customer pricing/checkout.
- `subscription_terms` holds `durationValue` + `durationUnit`, numeric `price`, and `discount`/`discountType`. Admin writes are fixed to 3/6/12 months (`duration_unit = 'month'`; 12 displays as "1 Year"); terms outside that set are retired (`is_active = false`), not deleted.
- The free plan is admin configuration: singleton `free_plan_settings` plus `free_plan_ad_limits` caps for one listing category or subcategory. Public `GET /subscriptions/free-plan` exposes the current sheet.
- `user_subscriptions` stores a purchase-time `priceUsd`, `subscription_category_id` group, `expiresAt`, `superseded_at`, and typed `superseded_reason` (`upgrade|replaced|expired|revoked`). A partial unique index enforces one current row per `(user_id, non-null group)`; different groups can coexist. Status is **derived** from expiry/supersede fields, not stored.
- Admin `POST /admin/user-subscriptions/:id/revoke` conditionally marks a current row `revoked`, keeps history, and reconciles the user's listings. Group-scope and free-plan edits enqueue a BullMQ reconciliation (a burst collapses into one waiting job; an edit during a running sweep queues one more behind it); the recurring 10-minute sweep is the backstop. There is no outbox handoff for this recomputable work.
- Deleting a group nulls existing subscriptions' group FK and cascades its catalog. Entitlement loading ignores null-group rows, so group deletion can remove a holder's allowance; confirm/migrate or revoke those subscriptions before deleting a live group. See [`apps/backend/src/admin/subscriptions/README.md`](apps/backend/src/admin/subscriptions/README.md) for lifecycle and remaining gaps.

### Reports (`reports.schema.ts`)

- `report_reasons`: admin-managed picklist, unique on `(targetType, reason)`, discriminated by `targetType` (`user`|`listing`).
- `user_reports`: `reporterId` → `targetUserId`, optional `reasonId` (set null on delete), `imagePaths` JSONB string array, `status` (`pending|approved|rejected`), `reviewedById`.
- `listing_reports`: `reporterId` → `listingId`, same status/reviewedBy pattern.

Admin list endpoints batch-lookup user names (reporter + target) via `inArray` to avoid Drizzle's double-JOIN alias limitation.

### App settings (`app_settings.schema.ts`)

The first runtime-tunable policy store (2026-11-08). One row per key: `key` (PK), `value` jsonb, `updatedById` (nullable, `SET NULL`), `updatedAt`. It exists because a moderation threshold has to change without a redeploy, while every other numeric knob in the backend is still an env var validated by `config.validation.ts`.

- **Five keys, allowlisted in code**, each with a type, a default and a zod parse: `reports.alert_threshold` (positive int, default 5, combined account+post counter) and `reports.post_alert_threshold` (positive int, default 5, post-only counter), plus `support.contact_email` / `support.contact_telegram` / `support.contact_phone` (optional strings).
- **Reads never throw.** A missing row, a malformed value or a parse failure returns the code default and logs; a settings row must never be the reason a login refusal or an approval fails.
- **No cache.** Readers do a single-row lookup where they need the value (the approval transaction, the login refusal), because the table is tiny and an in-process cache would reintroduce the cross-instance staleness the sweep work already fought.
- Admin surface: `GET /admin/settings` (all five, defaults merged in) and `PATCH /admin/settings/:key` (`@Roles('admin','super_admin')`, unknown key → 400, invalid value → 400).

### Attributes (`attributes.schema.ts`)

Single generic `attribute_options` table with a free-form `type` discriminator (`varchar(60)`, **not validated** — a typo'd type in the API silently creates a new set). Unique on `(type, slug)`. Optional `categoryId` FK + `subcategoryIds` JSONB (denormalized mirror of admin UI selections — **UUIDs, not slugs**, so client-side filtering must compare against the subcategory `id`).

**The scoping rule (`forSub` in `apps/web/actions/listings.ts`) — this is what makes unticking authoritative.** A set where _any_ row carries `subcategoryIds` is **managed**, and the ticks are the whole truth: a subcategory not ticked for a row does not see it. A set where _no_ row is linked anywhere is a **global picklist** and returns in full, so scoping can never silently empty a field. The rule is decided on the **set**, not on this subcategory's slice — the earlier "if nothing is ticked _for this subcategory_, return everything" had a nasty edge: unticking the last row of a managed set **resurrected the entire list**, so the field grew exactly when it should have emptied. Two consequences worth knowing: (1) the moment a row of a global set is ticked anywhere, that set flips to managed for _every_ subcategory at once; (2) a managed set that a subcategory simply has no ticks for renders **empty**, which is correct — `vehicles-for-rent` and `cars-for-sale` had no colour tick for a long time and only worked by the fallback. Admin CRUD at `/admin/attributes/:type`, served by the standalone `AttributesModule` (`src/attributes/`, `@Roles('admin', 'super_admin')`). The module also exposes **public reads** (`PublicAttributesController`, `@Public()`): `GET /api/v1/attributes/:type` (one set; admin pages + ad-hoc use) and `GET /api/v1/attributes?subcategoryId=<uuid>` (`listBySubcategory`, JSONB `@>` containment — ONE call returning every row linked to a subcategory; the web subcategory pages use this instead of per-type fetches). Note `AttributesService.list(type)` returns the full row (`id/type/slug/name/image/categoryId/subcategoryIds/sortOrder/isActive/…`) with **no `isActive` filter**, ordered by `sortOrder`.

**Data is seeded** (`src/attributes/seeds/attributes.seed.ts`, **insert-only** `onConflictDoNothing` — admin edits survive re-seeds). 19 types seeded (~279 rows): `colors, rams, cpus, storage_phone, storage_computer, screensize_laptop, screensize_monitor, bodytypes, enginetypes, vehicletypes, accessories, jobtypes, networks, bedrooms, bathrooms, facings, experiences, vgas, types`. The `types` picklist spans computer parts / cameras / TVs-audio / property / fashion / furniture / musical instruments; rows sharing `(type, slug)` (e.g. the many "Other - ផ្សេងៗ" rows) are merged by the seed's dedupe pre-pass, unioning `subcategories`. Seed slugs must match the DTO `SLUG_RE` (dev-time assertion throws otherwise).

**Images are never seeded** — every row starts `image: null`; admins upload via the admin UI (`ImageUpload` scope `attribute` → Supabase → public URL stored in `image`). Only 5 types are image-bearing (`hasImage: true`): `bodytypes, accessories, jobtypes, types, networks`. The single exception: after the insert loop the seed **gap-fills car body-type icons** (null-only UPDATE for the 9 car slugs → the web app's local `/sub-img/car_vehicles/cars-for-sale/body_type/*.png` assets; the `other-type` row maps to `other.png`) — non-null images are never touched. Since 2026-08-31 `BODY_TYPES` carries the full 21-row set (cars + lorries + the 5 vehicles-for-rent types motorcycle/bicycle/tuk-tuk-and-remork/city-bus/express-bus) in the **rent design order** (Motorcycle, Bicycle, Tuk Tuk, cars, buses, trucks, Other; convertible stays cars-only at its slot): one global `sortOrder` sequence keeps every subcategory's _filtered_ grid in its own design order, so re-seeds (insert-only) leave existing rows' links/order alone and the rent links + order on already-seeded DBs were applied as a one-time dev-DB SQL (the seed covers fresh DBs). The rental-type icons gap-fill from `/sub-img/car_vehicles/vehicles-for-rent/body_type/*.png`.

**`years` is generated, not stored.** `AttributesService.list('years')` computes `currentYear+1 → 1980` descending at read time (`categoryId` = cars-and-vehicles, `subcategoryIds` = cars-for-sale/motorcycles-for-sale, falling back to null/[]); `create`/`update`/`remove` reject `type === 'years'` with a 400.

**A type the web page doesn't know is invisible on the storefront:** the subcategory page renders only sets whose `type` appears in its `ATTRIBUTE_SET_TITLES` map (19 entries), so a newly seeded/admin-created type needs an entry there before it can appear as a grid. The DB currently carries three types outside both that map and the seed list — `condition`, `taxtypes`, `transmission` (2 rows each, all with empty `subcategoryIds`) — leftovers that render nowhere.

**Admin UI is trimmed to 6 types** — `lib/attribute-types.ts` (`ATTRIBUTE_TYPES`, the source of truth): bodytypes, accessories, jobtypes, types, networks, years (years is `readOnly: true`). Of the 19 seeded types, those 5 are manageable and the other **14** stay readable via the API but have no admin page/sidebar entry (spec-fixed plain dropdowns needing no management). `years` is the one managed type that is **generated, not seeded** — which is why the counts differ.

**`vehicletypes` is retired (2026-09-16, captain's call).** It and `bodytypes` held the **same 21 vehicle kinds** — every slug identical bar `other-type`/`other` — as two separate literals in `attributes.seed.ts`, neither derived from the other. Only `bodytypes` is admin-managed, so ticking a Body Type had **no effect** on the rent form, which read the duplicate instead; the rent browse page also rendered _both_ grids with 5 values appearing twice. `getVehicleTypes()` is deleted, Vehicles For Rent's **Vehicle Type** block now reads `config.vehicleKinds` (the same resolved list the `bodyType` block uses), and `vehicletypes` was removed from the browse page's `ATTRIBUTE_SET_TITLES`. **The 21 `vehicletypes` rows are still in the DB, unread** — deleting them is a separate decision. Ticking a Body Type row now controls both the rent form and the rent grid; each set is scoped by its `subcategoryIds`, so a value must be ticked for every subcategory that should offer it. **The sidebar is NOT derived from `ATTRIBUTE_TYPES`** — `components/dashboard/app-sidebar.tsx` hardcodes its own list, so a new type needs an entry in both; the hub (`dashboard/attributes/page.tsx`) _is_ derived and picks it up automatically. The dynamic route `dashboard/attributes/[type]/page.tsx` validates the slug against `ATTRIBUTE_TYPES` (404 otherwise) and renders `<AttributeManager type title hasImage? readOnly? />` (`components/dashboard/attribute-manager.tsx`). `readOnly` hides the Add button + per-row actions. Client-side search matches name/slug/category/subcategory names and resets to page 1.

**Browse filters (client contract, 2026-11-08):** `lib/feed-params.ts` is the only URL→feed translator on mobile (the counterpart of web's `apps/web/lib/search-params.ts`; the URL names intentionally differ). It emits the backend vocabulary only: `sort`, `postedWithin`, the three location slugs, `minPrice`/`maxPrice`, `condition`, `yearMin`/`yearMax`, `brand`, `attrs`, and the column booleans `hasDiscount` (`discount=1`) and `deliveryFree` (`delivery=1`). Discount and free delivery are listing columns, never `attributes` keys — legacy `attrs.discount`/`attrs.deliveryFree` are stripped, and the posting clients already keep them out of the JSONB. `attrs` is a JSON object capped at 12 entries with identifier keys and string/number values ≤120 chars, ≤2000 chars serialized; brand/model/body type/year compare the display names stored at post time. Inverted price/year ranges are swapped client-side because the backend 400s on `min > max`. Drill-down scope is route identity, not a filter: `brandId`, `typeId`, `attrKey`/`attrValue`, and the `brandScope=1` marker that the brand screen adds on a brand→bodytype navigation (a `brand` param without that marker is an editable filter). `/filters` returns to the originating route with `router.dismissTo` from an allowlisted route template and passes the scope back, and scope brands are excluded from the chip badge. `view` is presentation-only state carried in the URL so `/filters` can apply it in place; it never reaches the feed query. `countActiveFilters` is the single badge definition for the browse header and the Filters chip: one count per active filter row — each price bound, each `attrs` entry (Model, Job Type, Experience, …), one for date, year range, condition, location, discount, delivery, brand, non-default sort, and a route `attrKey`/`attrValue` tile until it is written into `attrs`. In Jobs the Category row switches the subcategory, so a jobs `subCategoryId` counts as one; other categories' subcategories are drill-down scope and do not count.

**Search (mobile contract, 2026-11-09):** `/search` is submit-driven. With no submitted `q` it lists device-local recents (`lib/recent-searches.ts`: AsyncStorage, newest first, max 10, case-insensitive dedupe, Clear; the pencil prefills the term for editing). Submitting stores the term and sets `q` on the route; results use the blue header with two navigation chips: `User` opens `/search-users?q=...`, `Post` opens `/search-posts?q=...` (the Company tab was removed on 2026-11-09 — the profile `company` field is not a usable company model). The default results view still shows the inline User preview and post list: the User section previews three rows and shows **Show More** when `meta.total >= 3`, opening the same `/search-users` page (20 per page, ending in `No more result!`). User rows open `/user/<username>`; the all-users page puts the paid badge on the right. `/search-posts` is the reference's search/browse page: the query in the header (X clears it to the browse state), the Filters/Location/Sort/Price row, the top-level category grid, the home banner, the sell promo and the existing listing feed; the Filters screen rounds back to `/search-posts` with every param, and the header bookmark opens saved ads. Post rows in the inline view use `SearchPostCard` (the reference's compact white card, 96 px image). Scoped opens from a category/brand/type keep their scope and search posts only (no chips, no `/users/search`). Typing never issues a request; only submit and Load More do. The entry state keeps the reference's light treatment; the results surface has dark variants. The results also show a Specifications card after the User preview: up to three matches from the public `GET /products?q=&limit=3`, a Show More button at three or more (the User card's rule), rows that open `/spec/<brandSlug>/<modelSlug>`, and Show More opening `/search-specs?q=` (all matches, `limit=200`); the card is hidden on scoped searches and when empty. Product matching prefix-matches each token over brand/model names and slugs, the same rule as the user search (captain, 2026-11-20).

**Product specs (mobile contract, 2026-11-10):** The listing detail renders a `View full specs` entry iff `GET /listings/:id` embeds `product` — a published spec row with an active brand and model; an unpublished page, an inactive brand/model or no `productModelId` all null the ref and hide the entry. The entry opens `/spec/<brandSlug>/<modelSlug>` (a dedicated mobile route, not web's `/product/...` path, because `/product/:id` is the listing detail and notification deep links open it with a listing id). The screen reads the public `GET /products/:brandSlug/:modelSlug` and renders `specGroups` in backend order; consecutive rows sharing a label fold into one label with multiple values (web's `foldRows`), the family chip uses web's five labels, and a `Fuel`/`Fuel Type` row yields the fuel chip. A 404 shows the not-found state, a transport/5xx failure shows Retry, and an empty `specGroups` shows the empty copy (web renders only the heading). Chrome is localized en/km; spec content and family labels stay as stored (English). The ad detail (`app/(categories)/product/[id].tsx`) also renders the same body inline below the seller profile, through the shared `components/product/ProductSpecBody.tsx`, when the fetched sheet has at least one group; the chip still opens this screen. No auth, no new endpoint, environment variable or dependency.

**Nearby (mobile location contract, 2026-11-10):** `hooks/useCurrentLocation.ts` reads the foreground permission on mount (never prompting) and requests it only on a tap. ## Known gaps (track as separate tickets)

- **Product Specifications are per model, not per trim/variant.** A car page carries `Years`/`Generation` and the rest as fields; trim-level pages (e.g. BYD Atto 2 45 vs 60) would need a variants concept and a post-form picker change. Phones' per-regional-model band lists are handled by the multi-value template rows; a true variants model — per-variant price, availability or a selector — is still absent.
- **Five listing categories require a published spec page.** `cars-for-sale`, `motorcycles-for-sale`, `phones`, `tablets`, `smart-watches` cannot be posted until staff create specs for their models. The `productSpec` key lives in each `field_schema`, which only `db:seed` writes (**never run the full seed on prod** — apply targeted `UPDATE subcategories SET field_schema = …` statements). The requirement is enforced in the web form only (the DTO stays optional); the picker caps at 200 published products per family, and the attached spec's family is enforced server-side.
- **Signed uploads are validated by the browser and the bucket, never by the backend** — `/files/sign` uploads bypass the backend, so the 10 MB / 2560 px / WebP rules live in `prepareImageForUpload` (client-side, 2026-11-04) and the bucket settings are the only server-side enforcement; a client that ignores the browser helper can still store an oversized object. Server-side multipart uploads _are_ checked, including the magic bytes. Also unchanged: (server-side multipart uploads — avatar, cover, feedback — are capped at 5 MB in multer and limited to raster image types). Ownership is enforced since 2026-10-23: user scopes (`listing`, `avatar`, `cover`, `chat`, `report`, `resume`) sign into `{scope}/{userId}/`, catalog scopes are staff-only, and `DELETE /files` lets non-staff delete only their own folders (`ListingsService.assertPhotosOwned` also proves listing photos are the caller's own uploads). Objects under the old flat `listing/…` paths stay valid on their listings but are never cleaned up.
- **Feedback rows do not own their images.** Deleting a feedback row leaves its storage objects behind; feedback images live in the default `listings` bucket under `feedback/…`, not a private folder.
- **CI covers the trees, not every surface.** CI gates PRs and `prod`; but stats, users CRUD, subscriptions and attributes have zero unit coverage, there are no admin-surface tests, and **`apps/mobile` has no type gate at all** (`expo lint` only — run `tsc --noEmit` by hand). Backend suite: **93 suites / 1328 tests** (verified 2026-11-02 on `feat/refine`).
- **Real SMS delivery is not end-to-end verified.** The PlasGate path (SMS outbox handler + `OtpSmsSender`) is unit-tested and fails closed, but no real send has been made against an approved sender id (task 1.7). The optional admin `GET /admin/sms-deliveries` read endpoint is not built (task 2.1).
- **Forgot-password limits are silent by design.** The reset request always answers `{ otpSent: true }` and does not return `retryAfterSeconds`, because the identifier may be a username/email that cannot be reserved against a per-phone limiter without revealing whether it exists; a user over the per-phone cooldown sees success but gets no SMS. The web form's resend timer is local (60 s). Social-only accounts with no phone cannot reset; phone-change OTP is still on Supabase.
- **`apps/mobile` is wired to the backend, with deferred surfaces still mocked.** See the Mobile app section. Chat is text-only (v2 E2E, REST polling) plus passcode restore; encrypted attachments, backup creation from the phone and the WebSocket are not implemented. The Resume (CV) builder is implemented (`/account/resume`, the 8-step wizard over the `/resume` API). Subscriptions/checkout, edit post, scan/QR, social sign-in/linked accounts and follower/following lists remain deferred with entry points hidden.
- **Category translations carry `en` + `km`** — 12 category + 146 subcategory `km` names live inline in `categories.seed.ts` (2026-10-21; the seed runner loops `en/km`). Field-schema `label` objects remain `en`-only. Admin category/subcategory create/update accept and return `nameKm` (empty string clears the km row).
- **Frontend UI translation covers marketplace + chrome + settings + /me + the sell flow + `/insight` + public profiles + the CV flow** — `apps/web/messages` has 28 namespaces / 1290 keys per locale. Auth, feedback, the legacy mock `DynamicForm` fallback, legal/help pages and admin `/wanderer` remain English. `lib/api/categories.ts` fetches brands/models with `Accept-Language: "en"` (proper nouns); attribute options carry `nameKm` (body types + car colours seeded), so those pickers show Khmer while the stored value stays the English `name`. Locations return `name` + `nameKm` and the web localizes them; the km listing detail resolves geo ids to `nameKm` and maps spec values through `nameKm`. Feed cards batch-resolve the page's province/district ids once; the likes/saved reaction cards still use the stored English location because that endpoint does not go through `getListingsFeed`. Client date labels use `lib/locale-labels.ts` because Khmer ICU data is not guaranteed.
- **Latent spec-vs-managed-set name divergences (all inert while the set is managed, the `bathrooms` hazard shape):** Fashion & Beauty `type` options (spec `Men's Accessories`/`Baby & Kids Clothing` vs rows `Men Accessories`/`Kid Clothing` — rows win); Furniture `type` options (spec plurals vs rows' singulars — rows win); the shared `other` row reads `Other - ផ្សេងៗ` app-wide vs plain `Other` in specs; jobs' inline job-type list (`Internship`/`Other` vs rows `Internships`/`Other-Jobs`) and `experiences` (rows `2 Year+` vs inline `2 Years+`). Unlinking every row would swap each form onto names no Browse grid can filter — deliberately left.
- **A typeless subcategory gets a dead grid if an admin ticks any `types` row for it.** 29 opted-in forms declare no `type`; all have zero ticks today. Ticking one grows a "Type" grid whose click resolves to `undefined` → legacy `bodyType` path → empty feed, no message. The guard is configuration: never tick `types` for those.
- **`photos` is the one schema key with no render gate** (`ImageUpload` renders unconditionally at max 8). Inert — all 146 declare photos — but check before opting in a form that doesn't.
- **A subcategory created through the admin UI still has no working post form.** `CreateSubcategoryDto`/`UpdateSubcategoryDto` carry no `field_schema` and the seed is its only writer, so such a subcategory gets a NULL schema and lands on the deliberately-unwired mock `DynamicForm` — it cannot publish at all. That makes `DynamicForm` + `EMPTY_OPTION_LISTS` **load-bearing, not dead code**; a real fix is a product decision. The mock data modules were deleted on 2026-10-30; `/sell` redirects to `/post`, and legacy numeric `-adid-` URLs 404.
- **Test/E2E debris has no cleanup path.** `listings.seed.ts` deletes junk by an exact-title list (7 cars-era strings), so later verification listings survive re-seeds. The demo catalogue now seeds ~124 listings across categories, but debris cleanup is still unaddressed (an `ILIKE '%E2E%'` pattern was proposed).
- **Idempotency completed-row hash reuse** — same key + different body returns the cached response instead of 422.
- **Legacy sessions without a `sid` cannot be revoked per device** until they refresh/re-login; admin and social/Telegram logins carry no device id. `users.tokensValidAfter` covers them after a password reset and now also on suspension (the two writers); other sign-out flows do not set it. An already-open chat socket is closed on the next send and now also closed by the suspension pub/sub signal, but an idle revoked socket can still receive pushes until it sends or reconnects.
- **Follower lists need a login, and `follow.created` is not transactional with the edge.** (1) The JWT requirement is what buys per-row `isFollowing` without an N+1. (2) `followUser` inserts, then notifies out-of-transaction: a notification failure 500s after the follow commits (self-healing — the `.returning()` guard prevents duplicates — so the worst case is a lost notification, never a wrong one).
- **Anything touching the migration watermark: check it first.** drizzle-orm 0.36.4's migrator compares only the _newest_ `created_at` in `drizzle.__drizzle_migrations` against each journal `when` (no per-hash check), so renumbered or older-stamped unapplied files are **silently skipped**. It bit the dev DB once (`0023`–`0026` re-run risk, repaired 2026-09-28, backup `drizzle.__drizzle_migrations_backup_20260928`) and renumbering has happened again since — simulate before trusting `db:migrate` on an old DB.
- **Mock profile URLs no longer resolve.** `/[username]` and `/[username]/about` look the handle up against real accounts (`GET /users/by-username/:username`) and `notFound()` otherwise — old demo handles 404 by design. `lib/user.ts` is still live (its `User` type is the profile render contract; `toProfileUser` adapts onto it).
- **Delete-account is a 90-day recovery window, not an instant wipe (2026-10-05).** `DELETE /users/me` (body `{password}`, bcrypt-checked) soft-deletes but deliberately keeps `primaryPhone`/`user_phones` — those are what the password-login reactivation path matches on. `AccountPurgeService` hard-deletes after the window (`ACCOUNT_RETENTION_DAYS = 90`, shared with AuthService on purpose); all FKs cascade.
- **Geography names are en/km** — `GET /locations/...` returns `name` + `nameKm` (2026-10-21); the web shows `nameKm` on `/km` and sorts by it. Villages deliberately unmodelled; the data file is a checked-in snapshot.
- **`PublicUser` over-exposes cross-user fields** (`GET /users/:id` returns `Omit<UserRow,'passwordHash'>` — includes `deletedAt`, verification timestamps). Narrow to an allow-list.
- **Attribute `:type` param is unvalidated** — any string silently creates a new set (`varchar(60)`); consider an allowlist.
- **No push notifications for chat** (no FCM/APNs — a backgrounded app catches up on its next poll); **legacy chat images are public-bucket URLs** (no migration); **WS send rate limiting is per-instance** (`sendTimestamps` is in-memory); the REST throttler now uses a shared Redis store.
- **Inline `field_schema` duplication** — ~10 forms are byte-identical to `commonListingFields` yet re-inline all 11 fields; a one-time systemic DRY pass, never per-ship.
- **`super_admin` vs `admin`: a tier split, plus account-management policy (2026-10-26).** The guard matches roles literally, so `@Roles('admin')` excludes a `super_admin`; super_admin's mandate is stats, reports, team, feedback and advertisements, and the sidebar mirrors that through each menu item's `roles` field. Every admin user mutation goes through `assertCanManageUser`: only `super_admin` may grant staff roles or edit/suspend/delete an `admin`/`super_admin` account, nobody may delete, demote or suspend themselves, and the last active super_admin can never be removed. The Users page form still offers `super_admin` to regular admins (backend 403s; hide the option later).
- **User-facing surfaces are real data.** Real: the `/me` header, home Browse-By-Category + Latest Ads + Trending, every category/subcategory feed + browse bar, listing detail, the post form (all 146), `/all-ads`, `/search`, `/notifications`, `/settings/*`, `/me/{likes,saved,followers,following,applied-jobs,job-applications,resume,about,subscriptions,billing-addresses}`, `/insight`, `/feedback`, the public profile, the report dialogs and the admin report/feedback queues, the premium checkout and Manage Ads. Mock data modules were deleted on 2026-10-30; `/me/membership` is a redirect.
- **Catalog images have no Storage backing** (2026-09-10 audit: 154 rows point at bundled `/sub-img` files, 152 at objects that are gone). All render as the no-image state by design; **captain's decision: leave it imageless** — do not re-add bundled paths or static fallbacks.
- **Specs-grid brand links are best-effort** (`slugify(attribute name)` can diverge from `brands.slug`; model links only highlight). Carrier icons cover 4 carriers (Qube/unknown → letter badge).
- **Schema-driven More Filters labels are English-only.** The dialog renders one select per `field_schema` `select` field and AND-s them through the feed's `attrs` param; known keys use `Specs.attributes` translations, the rest fall back to the schema's English label, and inline option names have no Khmer variants.
- **`generateUniqueUsername` race** — check-then-insert with no 23505 retry; concurrent same-name creates can 500.
- **`phoneVerifiedAt` is stamped by the OTP change-phone flow and by login/registration OTP verify** (refine's "Reliable SMS delivery" task 1.5). Changing `primaryPhone` without an OTP (`addPhone`, `setPrimaryPhone`, the auto-promotion in `removePhone`) clears it, since the column means "the CURRENT `primaryPhone` was verified" and there is no per-number record. Existing users are not backfilled. A soft-deleted user keeps its globally-unique `user_phones` row, so a re-registered user can have `primaryPhone` but no `user_phones` row (the About page falls back to it).
- **Moderation is prod's model with v1's phone ban layered on (2026-10-24 merge; split into delete vs inactive 2026-11-08).** Staff take ads down via `/admin/listings/:id/remove` (permanent: `deletedAt`, restore refused) or `/inactivate` (reversible, staff-only in both directions), or by approving a listing report; `listings.moderatedAt`/`moderatedById`/`moderationReason`, owner blocked from edit/publish (`LISTING_REMOVED_BY_ADMIN`), public `GET /listings/:id` 404s. Users file reports via `/reports/listings|users` (one pending report per reporter+target). `banned_phones` still blocks registration, OTP and phone changes with `PHONE_BANNED`, but **nothing writes to it any more** — approving a user report suspends the account instead, and no admin ban action or unban endpoint exists, so a lift is a manual `banned_phones` delete. Evidence uploads under `report/{userId}/` in the default bucket (unguessable, not private). Not yet: the owner's My Ads page does not explain a removal; an appeal record (who was suspended, whether it was overturned) is not tracked anywhere; Manage Advertisement Ads and an admin Payments page are not built.
- **Username login matches lowercase handles, but mixed-case admin handles need exact casing** (admin create/update keep the typed casing); profile lookup and uniqueness are case-insensitive since 2026-11-19. `UpdateProfileDto` names have no `@MaxLength` (22001 → 500 on overflow).
- **`src/tenant/` is a design doc, not code** — a proposed `tenants`/`tenant_members` schema for `payment_transactions.tenantId` (currently a bare UUID) and possibly `user_subscriptions`; no schema file, migration or export exists.
